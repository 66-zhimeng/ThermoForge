# Active Plan

## Objective

让模型实验室（`category=lab`）成为**自治**通路：Agent 自己写模型代码、自己在
真实数据上训练与测试、自己读指标改代码，闭环里不含任何人工审批环节。

## Assumptions

- 可复现性由机器判定保证，不由人工审批保证：五连检（接口 / 拟合预测 /
  save 契约 / save-load 往返位级一致 / 同种子重训位级一致）+ 环境锁 +
  子进程隔离 + 源码内容哈希。
- 「这个建模假设好不好」由证据淘汰，不由人排队放行；因此 `validated` 即可
  进正式实验，`deprecate` 是事后否决且不阻塞任何一轮循环。
- **预处理审批的人工门禁保持不变**：它改的是数据（会产生 vault revision），
  与实验室改假设不是一回事（DD-02 修订记录，2026-08-17）。
- 静态扫描是候选代码执行前唯一的自动关卡，是粗筛不是内核沙箱；该风险敞口
  明知并接受（同上）。
- 改模型 = 提交新版本（内容哈希一变即 `v(N+1)`），历史实验因源码快照冻结在
  实验目录而不被改写。

## 提示词装载（本次一并修复）

发现四个位点没有一个真正走 `prompts.load()`：`agent.py._default_system_prompt()`
直接读 `system.md` 原文（技能不进提示词），副驾与规划器各用代码内常量
（`copilot.md`/`planner.md` 无人读取），`mcp.md` 根本不存在。`prompts.py`
承诺的「装技能 = 改文件，四处行为一致」一处都没兑现，技能书成了死文档。

修法：四个位点统一走 `prompts.load()`，代码内常量降级为文件缺失时的兜底；
`load()` 增加 `$name` 占位符填充（`safe_substitute`），只用于**代码派生的
事实**（页面清单、界面工具名），决策规则一律写死在文件里；补上 `mcp.md`。
回归测试用哨兵文件替换 `PROMPTS_DIR`，验证四个位点都跟着变。

装载后的提示词规模（含绑定技能）：cli ≈ 7.4k tokens、planner ≈ 6.5k、
mcp ≈ 6.6k、copilot ≈ 0.7k（副驾不绑技能）。mcp 那份进的是 MCP 握手的
`instructions`，对每个外部 agent 会话都生效——嫌重就把 `SKILL_BINDINGS["mcp"]`
改成 `()`，一行的事。

### 3. 三个平台缺陷（本轮暴露并修掉）

- **R² 不是可声明的验收字段**。`Acceptance` 只有 CVRMSE/MAPE/NMBE 且
  `extra="forbid"`，需求方给的 R² 目标此前只能人工换算成 CVRMSE，而换算
  依赖当轮评估窗的 `CV_y`，换个窗就失真。→ 加 `r2_min`，编排器与发布门禁
  同时判，schema 已重导，回归 `test_r2_min_is_machine_checked`。
- **判据面声明了却不算**。编排器建实验时固定只给 `temporal_split`，目标
  声明 `evaluated_on=rolling_cv` 时验收指标恒为 `None`，每轮都判不了——
  这正是 8-18 网页版那两轮（EXP-0083/0084）空转的病根，8-19 的 EXP-0089
  又踩了一次。→ `_validation_spec()` 按目标的判据面补开滚动块，规划器显式
  给的参数不覆盖。回归 `test_rolling_cv_enabled_when_goal_judges_on_it`。
- **G3 同源阈值一刀切**。`same_origin` 在 |r|>0.98 直接判 blocker，把冷却塔
  两个目标全拦下（0.982 / 0.983），而 `derivation_chain` 明确无派生交叉——
  高相关是物理耦合（进水温→出水温、频率→功率），不是循环论证。→ 阈值做成
  可覆盖参数（`tf_dataset_modelability(same_origin_corr=)` /
  编排器 / `--same-origin-corr`），用了什么值写进报告 artifact 可查。
  本轮取 **0.995**：塔的两个放行，而已知的真循环论证
  （`power~current_percent` r=0.9955）仍然拦得住。

另外给每轮记录加了 `acceptance_unmet`（差在哪一项），进规划器的证据摘要——
只给「当前最优 CVRMSE」时规划器读不出「R² 还差多少」，容易原地重复同一个计划
（8-18 第 2 轮就是原样重交，指标逐位相同）。

### 4. 无人值守循环

`scripts/autoresearch.py`：与网页版同一个编排器、同一个 LLM 规划器
（`harness/prompts/planner.md` + 绑定技能），区别是**没有轮次上限**
（`--max-rounds` 默认 10000，实际停在编排器的停止条件上）、**多目标轮转**、
**状态可外部观测**（`research/autoresearch_state.json` + `autoresearch.log`）。
一整圈所有目标都没产出新轮次 → 判定「跑不动了」退出。

额度/鉴权类错误单独识别，写 `status=fatal` 退出，交给值守流程。
`scripts/notify_mail.py` 负责发信（SMTP 参数只从环境变量读）。

当前命令::

    python scripts/autoresearch.py --goals RG-0016,RG-0017 \
        --no-gain-rounds 5 --reopen --same-origin-corr 0.995 --guidance "..."

`--reopen` 只把停在**环境问题**（门禁未过/缺变量/覆盖不足）的目标转回
active；研究做完了的（达标/无增益）不动。重开会在账本留转换记录。

### 5. 「模型实验室自治」对编排器此前并不成立（本轮补上）

RG-0017 跑到第一轮就停在 `human_confirmation_required`，规划器自己写的
停止理由是：现有模块都表达不了风机定律 `P = n·a·(f/50)^b + c` 的台数×频率
幂律交互，**要人代它 `tf_lab_submit`**。

病根：模型实验室的自治闭环只对**会话式 agent** 成立（它能调工具），对
**编排器的规划器**不成立——规划器是单次吐一份实验 JSON 的角色，协议里
只有 `view_id` + `model`，没有提交代码的通道。提示词却写着「走模型实验室
tf_lab_submit」，于是它照做不了，只能停下来要人。

补法：计划里可以直接附 `lab_module {name, source, description}`，编排器
在建假设之前替它提交，过 AST 扫描 + 子进程五连检就在**同一轮**以
`category=lab` 引用（引用锁到 `name@vN`，避免并发提交后指向别的版本）。
校验没过不是致命错——把失败明细记成本轮失败，规划器下一轮能看见「哪一项
没过」并改代码，正是实验室设计里那个闭环，只是主体换成了编排器。
安全性仍由实验室自己的门禁保证，没有新开口子。

⚠ 实现时踩到一个真 bug：`_record_failure` 在无增益 streak 未满时返回
`None`，若把它直接当 `_run_round` 的返回值，本轮会带着一个**根本没入库的
模块**继续跑（TFML-003 直接崩）。所以 `_submit_lab_module` 必须把「本轮
作废」和「停止决定」分开返回。回归 `test_lab_module_failing_the_gate_*`。

### 10. 冷却水泵流量：两条口径分开，what-if 口径结案为缺测点（2026-08-19 凌晨）

需求方提问「水泵流量是不是要把多台泵一起考虑，流量与频率的关系应该是……」，
按这条线复核，查出两处实质错误，并据此把目标拆成两个口径。

**（1）台数自由度未被激发。** 冷却水泵 **99.5% 的时间是 3 台在跑**
（1 台 8 行、2 台 109 行、4 台 42 行）。当时最好的模块 `cwp_bank_affinity_v1`
里写的 `n × f_norm` 交互项，n 恒为 3，**实际退化成纯频率缩放**——它以为自己
在建「台数×频率」，其实只建了频率。
（附带：台数真变时正确形式也不是 `Q ∝ n·N`。并联 N 台对上系统阻力曲线
`H = kQ²`，解得 `Q = n·N/√(αN² + β)`——**加泵是饱和的，不是线性的**。
这份数据标定不出 α、β。）

**（2）原白名单混入了流量的下游后果量。** 实测 `Q·|ΔT|` 的变异系数只有
**0.080**（Q 自己 0.164），`corr(Q,|ΔT|) = −0.839` —— 这是能量守恒
`Q·ΔT ≈ 排热量/cp` 显形，**ΔT 是被流量决定的，不是原因**。用它建出来的是
虚拟流量计（流量计失效时顶替，合法），不是 what-if 模型。
注意：这**不违反 DD-16**（ΔT 不是由流量算出的列），同源检测也抓不到
（0.839 < 0.98 阈值）——是**用途层面**的判断，只有懂这个回路的人看得出来。

于是拆成两个目标：

| 口径 | 目标 | 白名单 | 最好成绩 |
|---|---|---|---|
| 虚拟流量计 | RG-0021 | 含 `delta_t`/`power_total` | R²=0.764 / CVRMSE 4.12% / NMBE +1.49% |
| **what-if** | **RG-0022** | 只有可操纵量 + 工况配置 | R²=0.340 / CVRMSE 8.05%（EXP-0149）|

两者之差就是「下游后果量贡献了多少」，那部分对 what-if 一点用没有。

**RG-0022 结案：R²≥0.90 在当前测点配置下不可达，瓶颈是缺测点。**
规划器自己给出的正式结论（已留痕在停止记录里）：

> 瓶颈不是模型形式，而是输入信息不足：`flow_total` 的同频残差 ±8.5% 来自
> 系统阻力变化（阀门开度、支路投运组合），而阀位与投运组合没有测点；
> `run_count` 99.5% 恒为 3，台数自由度未激发；`freq_mean/freq_max` 只能给
> 转速单维信息。候选输入内无论换 estimator、加交互、做分段或上实验室模块，
> 都无法创造不存在的系统阻力信息。

**建议补的测点（按优先级）**：①每台泵支路流量或泵前后压差 ②泵出口总管
电动阀/旁通阀阀位 ③冷机冷凝器支路开闭状态；若能提供**逐台泵频率**而非仅
群平均，更佳。预估收益：仅补一个总管阀位约能把滚动 R² 提到 0.70~0.80；
要稳定到 0.90，需形成「逐台支路开闭 + 逐台频率」的物理泵曲线模型，
并以压差或支路流量校验。

**现有模型仍可用的口径**：系统阻力状态不变（同一 `chiller_run_count`、
阀位固定）的短期工况内，`Q = 84.2·f − 551.4` 可作粗 what-if 线性外推，
但必须标注 CVRMSE 约 8.1%~11.6%，**不得用于跨阀位或跨投运组合的寻优**。

> 至此今晚有**四处**结论指向同一件事——瓶颈是缺测点而非缺模型：
> CH01/CH03 制冷剂侧、塔风机风量侧、冷冻水泵（判据面失效）、冷却水泵阀位侧。
> 这四条应合并成一份给现场的加表清单。

### 12. 方法论：验收判据要按物理量选，不能一律用 R²（2026-08-19）

今晚在**四个**地方踩到同一个坑（塔风机周折、CH03 退化折、冷冻水泵、冷却水
泵），代价是好几轮空跑，所以固化成规矩。

**根因**：`R² = 1 − (CVRMSE/CV_y)²`。R² 的分母是**判据窗内**目标自身的波动。
窗内目标近乎常数时，`CV_y → 0`，再小的误差都会让 R² 崩到负值——此时 R²
衡量的是「这一折目标波动大不大」，不是「模型好不好」。

**建目标前必做的一步**：算**判据面窗口内**的 `CV_y`（不是全集 CV_y），
按下表选判据：

| 窗内 CV_y | 判据 | 本项目实例 |
|---|---|---|
| > 0.15 | `r2_min` 可用，R² 有判别力 | 冷却塔逼近度（制冷季 0.266）、出水温（0.240）|
| 0.05 ~ 0.15 | R² 可用但要看逐折分布，警惕退化折 | 冷却水泵流量（中位 0.090）|
| **< 0.05** | **改用 `cvrmse_max` + `nmbe_abs_max`，不设 `r2_min`** | 冷冻水泵流量（0.010~0.084）、塔风机周折（0.038）|

需求方 2026-08-19 已确认：「可以改验收标准，我只是举个例子，大概的范围」——
R²≥0.90 是方向性要求，不是逐目标的硬约束。**按物理量类型分开定，并在
目标 `purpose` 里写明为什么这么定**（该判断会随目标进账本，事后可查）。

反向的坑也要防：判据太松等于没判据。定门槛的做法是**取已知最好成绩再紧
一档**（如冷冻水泵已知 CVRMSE 2.66% → 门槛 2.5%），逼出真实改进，而不是
把门槛设在已达成的水平上。

相关：规划器在 RG-0024 上**独立推出了同一结论**并主动收工，理由已留痕
（§「规划器停止理由必须留痕」）——说明这条规律对模型也是可发现的，
把它写进目标定义能省掉一整轮。

**影响范围已查清**：按 `code_version` 是否为 `0b7c1dc` 之前，逐个筛 104 个 lab
路线实验，命中 10 个（EXP-0057~0066），全部属于 RG-0012 / RG-0013。**已发布的
模型包无一来自这 10 个实验，生产环境干净。** 两个干净重跑仍满足各自判据
（5.28%≤12%、1.82%≤3.2%），已发布为 `wx-chiller-power-static@1.0.0` 与
`wx-hx-heat-transfer-static@1.0.0`。

教训：`code_version` 是实验工件里唯一能发现这类问题的字段。复现性不变量说的是
「同机器 + 同 lock 逐位可复现」，跨 code_version 不在保证范围内——所以**任何跨
提交的历史指标在引用前都该重跑一次**，尤其是走 lab 路线的。

## RG-0023 第一轮：七轮里五轮废在「看不见的报错」（2026-08-20）

重开后 7 轮，只有 2 轮产出实验，最优 **10.49%** —— 而直接三参数拟合的地板是
池化 1.79%。两个独立原因：

### ① 门禁失败明细被截断，规划器蒙着眼改代码（已修）

5 轮全废在 `tf_lab_submit`，拿到的 detail 只有一句概括：

    第2轮  实验室模块 'pump_affinity_efficiency_v1' 未过校验: [TFML-002] 结构校验未通过
    第3轮  实验室模块 'pump_power_efficiency_v1' 未过校验: 静态扫描不通过：按 violations 逐条改源码后重交

真正能照着改的东西在信封里一直有：AST 失败时 `summary["violations"]` 是逐条
违规，五连检失败时 `summary["validation"]["checks"][].detail` 是逐项说明。但
`_submit_lab_module` 写的是 `summary.get("error") or summary.get("validation")`
—— `error` 永远非空，后两者从来取不到。这段 detail 正是下一轮喂给规划器的证据，
所以它连着五次拿到同一句废话，改不动代码。

修法：新增 `_lab_failure_detail(env)`，把违规项与未过检查摊平进 detail（只列
没过的，过了的不占篇幅）。测试 `test_lab_gate_failure_detail_carries_actionable_specifics`
按两种真实信封形状钉住。

这是本轮第二次同类缺陷 —— 前有「规划器停止理由被丢掉」「失败轮明细不落盘」。
共同模式：**异常路径上的可操作信息被一句概括吃掉**。

### ② 模块没按 object_id 逐台标定

仅有的两轮成功里最好的 `pump_power_efficiency_v2@v1` 的 `fit()` 完全没碰
`object_id`，把 8 台泵拟合成一条全局曲线。这 8 台功率均值 66~103 kW、相似定律
指数 2.52~3.31，一条曲线结构上就做不好，10.49% 与此完全吻合（对照塔风机的
`ct_fan_tower_shared_b` 是用了 object_id 的）。两张视图都带 `object_id`，是模块
自己没用。guidance 已把「fit 必须按 object_id 分组标定」写成首要条目。

### 逐台三参数基线（样本内，供对照）

| 台 | a(kW) | b | c(kW) | CVRMSE |
|---|---|---|---|---|
| CHWP01~04 | 231~236 | 2.52~2.66 | −11~−18 | 1.10~1.30% |
| CWP01/03/04 | 187~192 | 3.09~3.19 | +1.8~+3.2 | 1.35~1.69% |
| CWP02 | 186.5 | 3.31 | +6.8 | **4.68%** |
| 池化 | | | | **1.79%** |

两个物理发现：**冷却侧 b≈3 且截距为小正数，符合相似定律；冷冻侧 b=2.52~2.66
且截距 −11~−18 kW 不物理**。并联泵辨识已定 σ=0（无静压），所以 b<3 不是静压
造成的，更可能是电机/变频器效率随转速下降 —— 拟合拿负截距去补，b 与 c 互相
抵偿。CWP02 是唯一异常台（4.68%，其余 3~4 倍）。

## RG-0023 第二轮：一轮达标，并挖出「逐台模型打不了包」（2026-08-20）

修掉门禁失败明细截断 + guidance 把「fit 必须按 object_id 分组标定」写成首要
条目后重开，**第 1 轮就达标**：`pump_power_per_object_affinity_v1@v1`，滚动面
CVRMSE **1.86%**（判据 3%）、NMBE 0.15%、R² 0.990、MAPE 0.99%，零失败轮。

同样的数据、同样的判据、同样的函数形式，差别只在 `fit()` 用不用 `object_id`：
**10.49% → 1.86%**。这坐实了上一轮的诊断。

真实性交叉验证：`code_version` 为泄漏修复之后；模块只读 `frequency` 与
`object_id`，结构上碰不到目标列；标定出的系数与独立手工拟合逐台吻合
（a 差 <2%，b 差 <0.1，c 同号同量级）。

物理结论确认：**冷却侧 b=3.00~3.125、截距 +0.2~+1.7 kW，就是相似定律
P∝f³；冷冻侧 b=2.575~2.75、截距 −7.8~−14.6 kW 为负、不物理**（σ=0 已排除
静压，指向电机/变频器效率随转速下降）。

**CWP02 是唯一异常台**：A 面 CVRMSE 15.86%、NMBE +6.94%，其余七台 0.9%~3.8%，
高一个数量级。这是测点/机械问题，不是建模问题 —— 建议查该泵功率表。

### 打包侧的契约裂缝（已修）

发包时 `KeyError: 'object_id'`。两处口径不一致：

- runner `_child._model_frame`：给模型「视图特征 + object_id/timestamp」
- 打包 `build_model_package`：`model.predict(golden_df[feature_order])`，只给特征

于是**任何按 object_id 分组的模型，实验里跑得通、打包必崩**。这是「堵目标列
泄漏」那次修改立下 `_model_frame` 契约后，打包侧没跟上留下的裂缝。

修法：新增 `BOOKKEEPING_COLUMNS`，`boundary_rows` 原样带出记账列（不做数值
转换 —— 它们是分组键不是模型输入），predict 调用与 `_model_frame` 同口径。
冒烟回放与在线推理本来就是「非 output__ 列全传」，所以自洽。回归测试
`test_boundary_rows_carry_bookkeeping_columns` 钉住。

已核查 `wx-ct-fan-power-unit@1.1.0` 未被同一问题静默影响 —— 该模块是全局
密度修正，不引用 `object_id`。
