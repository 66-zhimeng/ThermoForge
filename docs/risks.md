# 可行性风险与早期验证

方案讨论阶段的核心任务不是把方案讲得更完整，而是**尽早找出会让方案失效的东西**。本文列出 ThermoForge 的主要风险，重点在「如何用最低成本提前验证」——其中多数不需要写代码。

每条风险包含：为什么可能发生、影响、早期检验方式、缓解措施，以及风险成立时的替代路径。

## 数据类风险

### R1 数据质量不足以支撑目标精度

**为什么可能发生**：[research-loop.md §1](./research-loop.md) 示例中的 `mape_max: 0.05` 是先验设定的目标。而模型精度上限由数据本身决定：传感器精度、采样周期、稳态比例、变量完整性。作为量级参考，ASHRAE Guideline 14 对小时级校准模型的通行判据约为 CVRMSE ≤ 30%、NMBE 在 ±10% 以内——5% 的 MAPE 目标相对激进。

**影响**：验收条件永远无法满足，闭环持续消耗预算却无法收敛；或者更糟——为达标而反复调整验证方式，最终交付一个过拟合的模型。

**早期检验**

1. 统计温差分布：若供回水温差常年只有 3–5 K，而传感器精度 ±0.2 K，则制冷量的相对误差已达 ±4–8%，功率模型精度不可能优于此量级。
2. 拟合一个最简线性基线，看残差量级。基线的误差水平就是「数据说了什么」的下界估计。

**实测结论（[data-survey §F4](./data-survey.md)）**：剔除循环特征后，线性基线在时间切分测试集上 **CVRMSE ≈ 0.12、MAPE ≈ 8.9%、R² ≈ 0.79**。而使用循环特征时 MAPE = 4.35%——恰好「达标」。这说明 `mape_max: 0.05` 很可能就是在循环特征下估出来的。另发现冷冻水侧单独使用时 R² 为负，信息主要来自冷却水温度。

**缓解**：**先测再定**。Phase 2 的第一个实验就是基线，用它标定可达精度，再据此修订 Research Goal 的验收条件，并把修订记为一条 Decision。

**若成立**：放宽精度目标，或把目标从「预测绝对功率」改为「预测相对变化/排序」——对优化控制而言，能正确排序不同策略的优劣往往比绝对精度更重要。

---

### R2 流量测量缺失或不可信

**为什么可能发生**：冷冻水/冷却水流量计在实际项目中是重灾区——常见问题包括未安装、安装位置不满足直管段要求、长期未标定、或 BMS 里的「流量」实为水泵频率换算的估计值。

**影响**：这是**最高优先级的风险**。流量不可信 → 制冷量不可信 → COP 不可信 → 物理模型的主干（`Q = m·Cp·ΔT`、`P = Q/COP`）全部失去基础，[DD-08](./design-decisions.md) 的曲线模型也无法标定。

**早期检验**

1. 检查 `source_kind`：是 `measured` 还是 `estimated`。
2. 看流量序列的形态：真实流量计有噪声；若曲线过于平滑、呈阶梯状、或与水泵频率完全成比例，多半是换算值而非测量值。
3. 与额定流量比对：长期恒定在额定值附近，通常意味着它是常数或估计值。

**实测结论（[data-survey §F2](./data-survey.md)）**：**确认，且比预期更严重**。冷水主机没有任何流量属性——蒸发器/冷凝器流量、蒸发器回水温度、冷凝器供水温度全都不存在。全系统仅有的两处流量中，冷却水总管流量是由冷冻水侧热平衡反算的公式，且最小值为 **−1837.83 m³/h**（负流量）。`P = Q/COP` 类单机物理模型在本数据上无法标定。

**缓解**：把「流量是否可信」作为数据画像的**显式检查项**并写入质量报告，而不是默认可用。

**若成立**：改用不依赖流量的建模路径——以电功率、温度和设备状态为输入的纯数据模型，或改选对流量依赖较弱的对象（见 [DD-12](./design-decisions.md) 关于表冷器的讨论）。

### R3 制冷量由功率反算，构成循环论证

**为什么可能发生**：部分 BMS 的「制冷量」并非独立测量，而是由 `Q = m·Cp·ΔT` 计算；个别站点甚至直接用 `P × COP额定` 反算。后者意味着制冷量是功率的确定性函数。

**影响**：用制冷量预测功率将得到近乎完美的指标，且完全没有价值。这类错误极隐蔽——指标越好越不容易被质疑。

**早期检验**：这是**最应该优先做的一项检查**，成本极低：

1. 计算 `cooling_capacity / input_power`（即 COP）的时间序列。若它几乎恒定或只取少数几个离散值，说明制冷量是由功率导出的。
2. 用温度和流量独立重算 `Q`，与 BMS 给出的制冷量比对。完全一致（而非在测量误差内接近）说明是同一个公式算的，不是独立信息。

**实测结论（[data-survey §F1](./data-survey.md)）**：**确认，且为最严重形式**。制冷量列的公式是 `load = 电流百分比 × 9672 / 100`，对全部 4 台冷机、全部运行样本，`load / 电流百分比` 的不同取值**只有 1 个**。而 `power ~ 电流百分比` 的 R² 为 0.958–0.987。

决定性证据：用 `load` 与用 `电流百分比` 预测总功率得到**完全相同**的指标（R² = 0.96633，MAPE = 0.0435）——它们是同一电信号的两种刻度。且 4.35% < `mape_max: 0.05`，**这个循环模型会通过验收**，没有任何自动检查会拦下它。

**缓解**：`variables.source_kind` 字段就是为此存在的，必须在建模前核实，不能默认为 `measured`。建议在 Dataset View 层面对「目标的上游派生链」做自动检查（见 [implementation-notes §4.4](./implementation-notes.md)）——本次发现的问题正是这类检查能自动拦下的。

**若成立**：把制冷量从候选输入中剔除，改用温度、流量、状态等一手变量。

---

### R4 工况覆盖不足，无法验证外推

**为什么可能发生**：拿到的数据可能只覆盖单个季节，或设备长期运行在窄工况区间（如冷冻水出水温度常年锁定 7 °C）。

**影响**：[research-loop.md §6](./research-loop.md) 的验证矩阵有多个维度无法填充；`extrapolation_required: true` 无法验证；模型的实际适用范围远小于宣称范围。

**早期检验**：对每个候选输入统计分布与联合覆盖——尤其是负荷率、冷却水温度、室外湿球温度的取值范围与分位数。做一张「工况覆盖热力图」，空白区域就是不可验证区域。

**实测结论（[data-survey §F5、F8](./data-survey.md)）**：整年 15 min 数据，室外温度 −18.2 ~ 36.2 °C，四季覆盖良好。但**冷机仅在 2025-04-11 ~ 10-17 运行**，有效样本 14,913 个（占全年 42.5%），冬季为板换免费冷却模式。更关键的是**冷冻水温差全年只在 4.57–5.05 K 区间变动**（0.5 K），负荷变化几乎全由流量承担，ΔT 项没有信息量。缺失 5.51% 且成整段，最长一段连续 13.8 天。

**缓解**：Model Package 的 `constraints.yaml` 必须记录**已验证工况域与禁止外推域**（文档已有此要求）。覆盖不足不必然阻断方案，但必须诚实标注模型的适用边界。

**若成立**：缩小模型宣称的适用范围，或补充数据（更长时间跨度、多站点）。

---

### R5 设备间差异过大，通用模型不成立

**为什么可能发生**：同一机房的冷水机可能型号、容量、变频/定频配置不同；即使同型号，运行时长和维护状况也会造成性能差异。

**影响**：留一设备验证（测试面 B/C）失败，[architecture.md](./architecture.md) 中「通用设备模型」的定位不成立，退化为每台设备一个模型。

**早期检验**：按设备分组画 COP–负荷率曲线。若曲线族形状相似仅有平移，归一化后通用模型可行；若形状差异显著，则不可行。

**实测结论（[data-survey §F3](./data-survey.md)）**：不是「差异过大」，而是**差异为零**。4 台冷机的 `condenser_return_t` 与 `evaporator_supply_t` 都是引用同一组表头单元格的公式，运行时数值完全相同；设备之间唯一的差异是各自的功率与电流。留一设备验证（测试面 B/C）在本数据上不成立。此外运行台数 90.6% 的时间恒为 3 台，「设备组合」维度同样无法覆盖。

**缓解**：引入基于额定参数的归一化特征（PLR 而非绝对负荷），归一化所需参数来自 `parameters` 表——这也是 [前提假设 A5](./scope.md) 的价值所在。

**若成立**：改为「每设备一个模型 + 共享结构与超参」的分层方案，通用性体现在建模流程而非单一模型。

## 方法与方案价值风险

### R6 混合模型相对基线无显著增益

**为什么可能发生**：两种情形都可能——数据充足时纯 ML 已足够好，物理项贡献有限；或数据太差时物理和 ML 都不行，混合也救不了。混合建模的收益窗口未必存在于当前数据上。

**影响**：这直接冲击方案的核心卖点。若混合不带来增益，「物理—数据混合建模系统」的定位需要重新论证。

**早期检验**：无法在实验前确定，但可以**把它设计为一个明确的判定实验**：同一 Dataset View 上并列跑纯物理、纯 ML、残差混合三条路径，比较三者在测试面 C 上的表现，以及残差项的量级占比（见 [DD-07](./design-decisions.md) 的强制配套要求）。

**缓解**：即使混合无精度增益，物理主干仍提供两项独立价值——**可解释性**与**训练域外的行为可控性**。方案价值不应只绑定在精度上。

**若成立**：把方案重心从「混合建模」调整为「带物理约束验证的数据建模」——物理模型的作用从预测主干变为**约束与校验**，这仍是相对纯 ML 管线的实质差异。

---

### R7 自主闭环产出的假设质量低于人工

**为什么可能发生**：假设生成依赖 Agent 对 HVAC 领域的理解。可能出现的失败模式：反复提出相似假设、被指标噪声误导、忽略数据质量问题而归因于模型选择、或产出看似合理但无法证伪的解释。

**影响**：这决定「自主」是真价值还是包装。若人工每轮都要纠正方向，系统的实际贡献仅剩实验执行的自动化——那是流水线工具的价值，不是研究系统的价值。

**早期检验**：设计一次**对照评估**：给定同一份数据画像和基线结果，分别记录 Agent 与领域专家提出的下一轮假设，事后用实验结果评价二者的信息增益。样本量小但足以暴露系统性问题。

**缓解**

- 假设必须**引用已有证据**（文档已有此要求），这本身就过滤了一部分随机猜测。
- 在停止条件中加入「连续 N 轮无显著信息增益」（文档已有）。
- 降低期望：一期把自主性定位为「在预定动作空间内的自动搜索 + 结构化记录」，而非「自主科学发现」。[scope.md §5](./scope.md) 的成功标准已按此设定。

**若成立**：保留完整的契约、数据底座、实验内核与模型包（这些价值不依赖自主性），把 Agent 降级为「实验编排助手 + 证据整理」，由人工主导假设。

## 落地与工程风险

### R8 契约过严，现场数据导不进来

**为什么可能发生**：[data-contract.md §5](./data-contract.md) 的硬性规则（禁合并单元格、禁公式、时间戳必须为带时区文本、单位必须登记、不得猜测列名映射）与现场 Excel 的真实形态差距很大。现场导出常见：多级表头、单位写在标题里、中文点位名、公式引用、缺失值用 `--` 或 `9999`。

**影响**：**第一份真实文件可能一条都导不进去**。若被理解为「工具不可用」，方案在落地首日就失去信任。

**实测结论（[data-survey §4](./data-survey.md)）**：**确认**。11 条硬性规则违反 6 条：111 个合并单元格、2,955,883 个公式单元格、4 行多级表头、时间戳为 Excel 序列号（无时区）、一个中文 `property_code`、`manifest`/`objects`/`variables`/`data` 四张必需表全部缺失。当前形态下导入器在第一步就会中止。此外表头行标签本身不一致——冷冻水泵表把「物模型」与「设备名称」两行内容写反了。

**缓解**：严格的契约本身是正确的——猜测性映射带来的静默错误比导入失败危险得多。但需要配套：

1. 提供**规范化预处理工具**（把现场 Excel 转为 TFDC-XLSX），将「修数据」与「校验数据」分为两个明确阶段，而不是放松校验。
2. 导入失败时输出**可操作的修复清单**（哪个 sheet、哪一行、改成什么），而不只是错误码。
3. 提供 TFDC-XLSX 模板与最小示例。

这三项建议应纳入 Phase 0/1 的交付范围。

### R9 Agent 成本与研究时长不可控

**为什么可能发生**：闭环设计为持续运行，每轮涉及多次工具调用与结果分析。若停止条件失效或假设生成陷入循环，成本会持续累积。

**影响**：单次研究的成本不可预测，方案难以推广。

**缓解**：文档已规定预算与停止条件。补充建议：

- 预算必须是**硬性中断**而非提示，超限即进入 `STOPPED` 并输出已有结论。
- 工具响应体设大小上限（见 [implementation-notes §11](./implementation-notes.md)），这是控制上下文成本最有效的单点措施。
- 记录每轮的 token 与时间消耗，使成本本身成为可分析的指标。

---

### R10 模型上线后收益无法验证

**为什么可能发生**：模型用于能效优化后，实际节能量需要与「不采取措施的基线」比较，而该基线不可直接观测。这是 M&V（测量与验证）的经典难题，会受天气、负荷、运行策略变化干扰。

**影响**：无法证明方案的业务价值，即使模型技术指标良好。

**缓解**：在方案阶段就把 M&V 方法纳入考虑——如保留对照期、采用 IPMVP 类方法建立调整后基线，或设计 A/B 交替运行时段。这需要在部署**之前**约定，事后无法补救。

**归属说明**：M&V 本身不在 [一期范围](./scope.md) 内，但接口需要提前预留：Model Package 应能记录部署时间点与生效范围，供后续分析使用。

---

### R11 传感器漂移导致在线退化

**为什么可能发生**：温度与流量传感器长期漂移是常态。模型在训练数据上正确，但输入分布缓慢偏移后预测系统性偏差。

**早期检验**：在历史数据中寻找已发生的漂移——如设备停机期间供回水温差应趋近于 0，若存在稳定的非零偏置，即为传感器零点漂移的证据。这类检查也能识别出不适合用于训练的数据区间（[research-loop.md §3](./research-loop.md) 已把它列为一类结构化发现）。

**缓解**：[model-package.md §7](./model-package.md) 的漂移证据回流机制正是为此设计。补充建议：把「停机时温差应趋零」这类**可自检的物理不变量**纳入在线监控，作为传感器健康度的独立信号。

---

### R12 单机性能撑不住

**实测结论**：**排除**。现有工作簿 43.8 MB、11 表、35,040 行 × 最多 72 列，用纯 Python + openpyxl 只读流式解析全量数据约数十秒，无内存压力。瓶颈确实在 Excel 解析而非查询（见 [implementation-notes §1.5](./implementation-notes.md)），但在当前规模下不构成问题。

**缓解**：[DD-06](./design-decisions.md) 的复审触发条件已覆盖此项。风险等级低，不应成为一期过度设计的理由。

## 建议的下一步

上述六项已于 2026-08-08 完成核实，结论见 [数据探查报告](./data-survey.md)。基于结果，下一步优先级为：

1. **确认数据性质**——工作簿有多项特征强烈提示它是仿真生成而非现场采集（[data-survey §F9](./data-survey.md)）。若确为仿真，本次测出的精度基线不能代表真实数据的可达水平，需另行获取现场数据。属 [开放议题 Q10](./open-questions.md)。
2. **解决 COP 量纲问题**——实测系统 COP 中位数 9.99~11.31，超出水冷离心机组的物理可实现范围（通常 5–7），且两种制冷量口径相差 p95 +62%。在此之前不应开展物理建模（[data-survey §F6](./data-survey.md)）。
3. **修订 Research Goal**——剔除 `load` 与 `电流百分比` 等循环输入，验收条件按实测基线重设。
4. **把派生链检查固化为自动规则**——本次发现的循环论证正是这类检查能自动拦下的。
5. **实现规范化预处理工具**（上文 R8 的建议 1），把这份工作簿转为 TFDC-XLSX，作为 Phase 0/1 的第一个真实用例。

这类核实应在**每次接入新数据源时重复**，而不是一次性动作。
