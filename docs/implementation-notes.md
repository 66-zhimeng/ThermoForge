# 实现细则与已知陷阱

本文记录从设计文档走向代码时会实际遇到的问题：库的行为差异、边界情况、容易被忽略的泄漏路径，以及需要提前统一的实现约定。

[工程约定](./conventions.md) 定义「规则是什么」，本文说明「代码里怎么落」和「哪里会踩坑」。标注 **[草案]** 的取值需用真实数据标定。

## 1. Excel 读取

### 1.1 必须使用只读流式模式

`openpyxl` 默认会把整个工作簿构建为对象树，一份 100 万行 × 100 列的 `data` 表可占用数 GB 内存并耗时数分钟。必须使用：

```python
wb = load_workbook(path, read_only=True, data_only=True, keep_links=False)
ws = wb["data"]
for row in ws.iter_rows(values_only=True):
    ...
```

- `read_only=True`：流式读取，内存恒定。代价是不能随机访问单元格，需一次遍历完成解析。
- `data_only=True`：读取公式的**缓存值**而非公式文本。注意：若工作簿由非 Excel 工具生成，缓存值可能为 `None`，此时无法区分「空单元格」和「未计算的公式」。因此公式检测必须**另开一次** `data_only=False` 的遍历，或直接检查 sheet XML 中是否存在 `<f>` 节点。

### 1.2 只读模式下检测不到的问题

`read_only=True` 时 `ws.merged_cells` 为空、`ws.max_row` 可能不准。合并单元格（`TFDC-105`）和外部链接（`TFDC-109`）的检测应直接在 xlsx 的 ZIP 结构上做：

| 检测项 | 位置 |
|---|---|
| 合并单元格 | `xl/worksheets/sheetN.xml` 的 `<mergeCells>` |
| 公式 | `xl/worksheets/sheetN.xml` 的 `<f>` |
| 外部链接 | `xl/externalLinks/` 目录存在 |
| 宏 | `xl/vbaProject.bin` 存在，或扩展名为 `.xlsm` |
| 1904 日期系统 | `xl/workbook.xml` 的 `<workbookPr date1904="1"/>` |

这些都是廉价的结构检查，应在解析数据**之前**完成，避免读完百万行才报错。

### 1.3 时间戳列

按 [conventions §3.1](./conventions.md) 的规定，`timestamp` 必须是文本单元格。实现要点：

- `values_only=True` 返回的若是 `datetime.datetime` 对象，说明它是 Excel 序列号 → 报 `TFDC-502`。
- 若是 `str`，用 `datetime.fromisoformat()` 解析（Python 3.11+ 支持完整 ISO 8601 偏移量），失败报 `TFDC-501`。
- 解析后立即转 UTC，后续管线不再见到本地时间。
- **不要**用 `pandas.to_datetime` 的自动推断解析整列：它在遇到混合格式时会逐行回退到 `dateutil`，性能塌陷且可能对 `01/02/2026` 做出与文件其他行不一致的日/月推断。应固定 `format=` 参数。

### 1.4 数值精度

Excel 单元格显示的位数与存储值不同。`3.14159265358979` 可能显示为 `3.14`，读出的是完整 double。反之，Excel 对超过 15 位有效数字的输入会截断。因此**不能**用「Excel 里看到的值」做测试断言，golden fixture 的期望值必须从解析结果生成并固化。

### 1.5 规模上限与逃生通道

xlsx 单表上限为 1,048,576 行 × 16,384 列。按 60s 分辨率，单表约容纳 **2 年**数据；变量数上限 16,383（扣除 `timestamp` 列）。

超出时的处理属于 [conventions §8 待决策 #5](./conventions.md)。实现上建议现在就预留：解析器接受 `data`、`data_2`、`data_3`… 的分片命名，按 `timestamp` 纵向拼接并校验无重叠。

另外，即使在限额内，openpyxl 解析百万行也需要分钟级时间。建议在导入器中设置阈值（**[草案：单文件 > 20 万行或 > 50 MB]**），超过时在报告中提示改用 `TFDC-Parquet` 载体——Excel 是交换格式，不该承担大批量回填。

## 2. 类型与缺失值落地

`pandas` 的默认类型推断会破坏契约语义，必须显式构造 schema：

| 陷阱 | 后果 | 做法 |
|---|---|---|
| `int64` 列出现缺失 | 整列被提升为 `float64`，大整数丢精度 | 使用 Arrow `int64` + null，pandas 侧用 `Int64` |
| `object` dtype 混装 | 静默接受脏数据 | 逐列按 `variables.dtype` 强制转换，失败报 `TFDC-404` |
| `bool` 列含空值 | 被转为 `object` | 使用可空 `boolean` |
| 空字符串 vs null | 语义不同却被合并 | 字符串列保留空串，报 `TFDC-603` 由人工判定 |
| `float32` | 与 double 指纹不一致 | 全链路统一 double，不做降精度存储 |

建议直接以 **Arrow Table** 作为导入器的内部表示，只在需要时转 pandas/Polars。Arrow 的类型系统能表达「可空整数」和「带时区时间戳」，而 numpy 不能，这在指纹计算（[conventions §5.2](./conventions.md)）中是关键。

## 3. Dataset View 物化

### 3.1 缓存键

物化结果的缓存目录名使用 `view_hash` 前 16 位，但目录内必须存放完整的 View 定义和完整哈希，加载时重新校验（`TFV-801`）。仅靠目录名匹配，在哈希截断碰撞或人为改名时会静默加载错误数据。

### 3.2 重采样必须与在线一致

离线 View 的重采样（左闭右开、标签取左边界、`min_count`）和在线推理的窗口聚合**必须是同一份代码**，不能一份用 pandas `resample` 一份在流式服务里手写。这是训练/服务偏斜（training-serving skew）最常见的来源，且症状隐蔽：模型指标正常，上线后系统性偏移半个窗口。

实现建议：把窗口聚合抽成不依赖 pandas 的纯函数（输入 `(timestamps, values, spec)`），离线批量调用、在线增量调用，两侧共用并有一致性测试。

### 3.3 长表转换

[data-contract §7](./data-contract.md) 要求把多设备实例转为长表（`object_id` + `property_code` 列）。实现注意：

- 转换后 `object_id` 成为**分组键而非特征**，必须显式声明它不参与模型输入，否则树模型会直接记住设备编号，留一设备验证时表现崩塌——而随机切分下指标反而更好看，容易误判为「模型很强」。
- 若不同设备的额定容量差异大，应引入归一化特征（如 PLR = 负荷/额定容量）而非直接喂绝对值，否则通用设备模型无法外推到未见机型。归一化所需的额定参数来自 `parameters` 表。

## 4. 数据切分与泄漏

### 4.1 时间切分不是按行数切

按行数切分在存在数据空洞时会导致边界落在意外的时间点。正确做法：先确定时间边界，再按边界筛选。

```text
1. 按 timestamp 排序
2. 取累积样本数的 0.70 / 0.85 分位对应的时间点
3. 边界向下对齐到 resolution 整数倍
4. train = [t0, b1), validate = [b1, b2), test = [b2, t_end]
```

边界必须记录在实验制品中，不能只记录比例——否则数据集 revision 更新后同一个 `0.70` 会对应不同的时间点，实验不可比。

### 4.2 Purge 与 Embargo

若特征包含滞后项（lag L）或滚动窗口（window W），紧邻切分边界的训练样本会包含验证集时段的信息。必须：

- **Purge**：从训练集末尾剔除 `max(L, W)` 时长的样本。
- **Embargo**：从验证集起始额外跳过 `E` 时长（**[草案：E = 1 个自相关时间尺度，冷水机系统建议 30–60 min]**），避免热惯性导致的短程相关泄漏。

未做 purge 时，含滚动均值特征的模型会在验证集上给出偏乐观的指标——这类问题在指标上表现为「验证集比测试集还好」，是明确的告警信号，应触发 `TFX-903`。

### 4.3 时间 × 设备的二维验证面

[research-loop §6](./research-loop.md) 的验证矩阵在实现上应落为三个独立测试面，而不是一个混合测试集：

| 测试面 | 设备 | 时间 | 检验什么 |
|---|---|---|---|
| A | 已见 | 未来 | 时间外推、传感器漂移鲁棒性 |
| B | 未见 | 已见 | 跨设备泛化 |
| C | 未见 | 未来 | 真实部署条件（最严格） |

发布门禁应针对面 C 设阈值。只报面 A 的指标会显著高估上线表现。

### 4.4 其他泄漏来源

| 来源 | 表现 | 防范 |
|---|---|---|
| 标准化/归一化在全量数据上 fit | 测试指标偏乐观 | scaler 必须在训练集上 fit，并随模型序列化 |
| 居中滚动窗口（`center=True`） | 特征包含未来值 | 只允许后向窗口 |
| 目标变量的滞后项作为特征 | 指标极好但无控制价值 | 若目标是被优化量，禁止使用其自身滞后 |
| 派生量与目标同源 | 例如用 `cooling_capacity` 预测 `input_power`，而前者由后者反算 | 检查 TFOM `expression` 依赖图，禁止目标的上游派生链进入特征 |
| 重复时间戳未去重 | 同一样本同时出现在训练和测试 | 导入层已保证唯一（`TFDC-503`） |

最后一条尤其要注意：HVAC 数据中 `cooling_capacity` 有时并非独立测量，而是由 BMS 用 `Q = m·Cp·ΔT` 算出，甚至有的站点直接用 `P × COP_额定` 反算。若是后者，用它预测功率是循环论证。`variables.source_kind` 字段（`measured` / `derived`）就是为此存在的，必须在建模前核实，不能默认为实测。

## 5. 指标定义

文档中出现的指标必须固定公式和口径，否则不同实验之间无法比较。以下为建议定义（**比率制，非百分比**，与 `acceptance.mape_max: 0.05` 一致）：

| 指标 | 公式 | 边界情况 |
|---|---|---|
| RMSE | `sqrt(mean((y-ŷ)²))` | — |
| MAE | `mean(\|y-ŷ\|)` | — |
| MAPE | `mean(\|y-ŷ\| / \|y\|)`，仅对 `\|y\| ≥ y_floor` 的样本 | 见下 |
| CVRMSE | `RMSE / mean(y)` | `mean(y) ≈ 0` 时未定义 |
| NMBE | `sum(y-ŷ) / (n · mean(y))` | 见下 |

### 5.1 MAPE 的零分母

冷水机在停机或极低负荷时功率接近 0，`|y-ŷ|/|y|` 会爆炸，少数样本即可主导整个指标。必须：

- 由 Research Goal 或 TFOM 声明 `y_floor`（**[草案：额定功率的 5%]**）。
- 剔除 `|y| < y_floor` 的样本，并在指标中一并报告 `mape_valid_fraction`。
- 若有效样本比例低于阈值（**[草案：80%]**），报 `TFX-905`，不得只报一个漂亮的 MAPE 数字。

更稳健的替代是 **sMAPE** 或直接用 CVRMSE。建议把 CVRMSE 作为主指标，MAPE 仅作参考。

### 5.2 必须补充 NMBE

当前文档的指标集（RMSE / MAE / MAPE / CVRMSE）**全部是绝对误差类，无法暴露系统性偏差**。一个恒定高估 3% 的模型和一个无偏但方差稍大的模型可能 RMSE 相同，但前者用于能耗优化会持续把工况推向错误方向。

建议将 **NMBE** 纳入必报指标，并在验收条件中单独设限。作为量级参考，ASHRAE Guideline 14 对小时级校准模型的通行判据约为 CVRMSE ≤ 30%、NMBE 在 ±10% 以内（月级为 15% / ±5%）。

> 顺带提示：[research-loop §1](./research-loop.md) 示例中的 `mape_max: 0.05`（5%）对小时级冷水机功率预测是相当激进的目标。这个值应在基线实验后依据实际可达水平修订，而不是先定死再逼模型达标——否则容易诱发过拟合和验证集选择偏差。

### 5.3 指标计算的一致性

所有指标必须由同一个函数在同一份预测结果上计算，禁止各建模脚本自行实现。差异往往出在：样本剔除口径、是否加权、多设备时是先聚合还是先分设备再平均（macro vs micro）。建议默认 **micro（全样本合并）**，同时附带 per-object 明细。

## 6. 物理约束检查

### 6.1 能量平衡的容差不是常数

`Q = m · Cp · ΔT` 看似简单，实现时有三处会引入误差：

- **流量单位**：`m3/h` 是体积流量，转质量流量需要密度。水的密度从 5 °C 的 1000 kg/m³ 到 35 °C 的约 994 kg/m³，用常数会引入约 0.6% 偏差。
- **比热**：水的 `Cp` 约 4.18–4.20 kJ/(kg·K)，在工作区间内变化约 0.5%。
- **温差本身的测量误差**：这是最大的一项。典型温度传感器精度 ±0.2 K，而冷冻水供回水温差常只有 5 K，相对误差即 ±4–8%。

因此守恒检查的容差必须是 `max(abs_tol, rel_tol · |Q|)` 的形式，且 `rel_tol` 需覆盖传感器误差传播，取 1% 之类的值会导致几乎全部样本被判违规。建议先用真实数据做一次误差传播分析再定阈值，并把所用的密度/比热模型（定值还是温度相关）记录在物理模型版本中。

### 6.2 可证伪的硬约束

比容差检查更有价值的是**物理上不可能**的约束，它们不依赖标定：

- `COP > 0`
- `COP < COP_Carnot = T_evap / (T_cond - T_evap)`（温度用开尔文）
- `input_power ≤ rated_power × 上限系数`
- 制冷量为正时 `input_power > 0`

违反这类约束的样本几乎必然是数据问题（传感器故障、时间错位、单位错误），应在数据质量阶段就标出，而不是留到模型验证。

### 6.3 单调性检查

单调性不能只在历史数据上看相关性——数据中的相关性是被控制策略耦合过的。正确做法是在**训练好的模型上**做受控扰动：固定其他输入于典型值，单独扫描目标输入，检查输出是否单调。

对树模型，XGBoost 和 LightGBM 都原生支持 `monotone_constraints`，应优先在训练时强制约束而非事后检查。注意该约束会牺牲一定拟合精度，且与部分特征交互设置不兼容，需在实验中记录。

### 6.4 违规率的定义

`physics_violation_rate` 必须明确口径。建议同时报告：

- 每条约束单独的违规样本比例。
- 总体违规率：**任一**约束违规即计入。

`acceptance.physics_violation_rate_max: 0.001` 应绑定到总体口径，否则容易出现「每条都恰好达标、合起来严重超标」的情况。

## 7. 可复现性

### 7.1 线程数环境变量必须在 import 之前设置

这是最容易踩的坑：`OMP_NUM_THREADS`、`OPENBLAS_NUM_THREADS`、`MKL_NUM_THREADS` 在 numpy/scipy **被导入后**再修改不生效，BLAS 后端在加载时就已读取。

Experiment Runner 必须以**子进程**方式启动实验，并在子进程环境变量中预置这些值，而不是在实验脚本内部 `os.environ[...] = ...`。这也顺带满足了 [architecture §4](./architecture.md) 中「Experiment Runner 隔离执行」的要求。

### 7.2 种子清单

单一 `random_seed` 不足以固定所有随机源，必须逐一设置并记录：

```python
PYTHONHASHSEED    # 子进程环境变量，影响集合/字典迭代顺序
random.seed
np.random.default_rng(seed)   # 使用显式 Generator，不用全局 np.random.seed
sklearn: random_state=
xgboost / lightgbm: seed / random_state, 且固定 nthread
train/validate 划分、交叉验证、数据打乱各自的种子
```

**固定线程数是复现的必要条件**：多线程浮点归约的累加顺序不确定，线程数变化会导致末位差异，在树模型的分裂点比较中可能被放大为不同的树结构。

GPU 训练默认不可复现，一期不建议使用；若使用必须显式声明并放宽复现容差。

### 7.3 复现容差

| 场景 | 要求 |
|---|---|
| 同一机器、同一 `environment_lock` | 指标 bit-exact 一致 |
| 同 OS 不同 CPU | 相对误差 ≤ 1e-9 **[草案]** |
| 跨 OS / 跨架构 | 相对误差 ≤ 1e-6 **[草案]**，且必须在实验记录中标注平台差异 |

超出容差即报 `TFX-901`。「复现」必须是可机器判定的断言，不能是人工目测两个数字差不多。

## 8. 模型序列化与冷加载

### 8.1 不要把 pickle 作为唯一交付格式

`pickle` / `joblib` 有两个硬伤：跨库版本不保证可加载（sklearn 明确不承诺兼容性），以及反序列化等价于任意代码执行。作为长期归档的模型包格式不可接受。

建议按模型类型分别处理：

| 模型类型 | 推荐格式 | 理由 |
|---|---|---|
| 物理模型 | YAML / JSON 明文参数 + 代码版本 | 可读、可审计、可人工复核，是物理模型的核心价值 |
| 树模型 | XGBoost `.json` / LightGBM `.txt` 原生格式 | 官方保证跨版本可读 |
| 线性/多项式 | 系数 JSON | 同上 |
| 通用/神经网络 | ONNX | 跨运行时，便于部署到非 Python 环境 |
| 兜底 | joblib + 严格版本锁 | 必须同时保存 golden 预测集（见下） |

预处理（标准化、特征顺序、缺失填充）必须与模型一起序列化，且**特征顺序要显式存储为列表**——依赖 dict 顺序或 DataFrame 列顺序，在跨版本加载时是定时炸弹。

### 8.2 Golden 预测集

模型包中应包含 `golden.parquet`：一组固定的输入样本及其在训练环境下的输出。冷加载冒烟测试（`TFM-1005`）不能只验证「能加载、能出数」，必须比对 golden 输出在容差内一致。

这是唯一能发现「模型加载成功但因库版本差异行为改变」的手段，而这类问题在生产环境往往表现为缓慢的精度衰减，很难归因。

### 8.3 冷环境验证

冒烟测试必须在**干净环境**执行：新解释器进程、按 `environment.lock` 重建的依赖、仅挂载模型包目录。在训练进程里跑一遍推理不算冷加载——训练时已导入的模块会掩盖模型包缺失依赖声明的问题。

## 9. 在线推理

### 9.1 签名需要声明历史依赖

当前 [model-package §3](./model-package.md) 的签名只描述瞬时输入。一旦模型使用滞后或滚动特征，签名就不完整——部署方无法知道需要准备多长的历史缓冲。建议扩展 **[草案]**：

```yaml
history_required:
  window: 30min        # 最长回看窗口
  resolution: 1min     # 期望输入分辨率
  min_samples: 25      # 低于此值拒绝推理
cold_start: reject     # reject | degrade_to_steady_state
```

冷启动、断线重连、历史空洞时，运行时**必须**返回明确的 `not_ready` 状态，而不是用可得的部分数据凑一个预测。控制回路拿到一个静默降级的错误预测，比拿到一个明确的失败信号危险得多。

### 9.2 超范围输入

`constraints.yaml` 需为**每个输入**声明超范围策略，而非全局一刀切：

| 策略 | 适用 | 说明 |
|---|---|---|
| `reject` | 关键输入 | 返回错误，不出预测 |
| `clamp` | 有明确物理上下限且边界处行为可信 | 必须在输出中标记已截断 |
| `passthrough_with_flag` | 轻微越界且模型外推可信 | 输出附带 `extrapolated: true` |

无论哪种策略，越界事件都必须计数并回流 Research Ledger——这是 [model-package §7](./model-package.md) 中「漂移证据」的主要来源之一。

### 9.3 延迟指标的口径

`inference_latency_ms_max: 5` 需要明确测量条件，否则不可验证：

- 批量大小（建议 `batch=1`，对应实时控制场景）。
- 预热次数（**[草案：先执行 100 次丢弃，再测 1000 次]**）。
- 报告 p50 / p95 / p99，验收绑定 **p99** 而非均值。
- 记录硬件指纹与线程数。

5 ms 的 p99 对树模型可达，对含大量特征工程的管线则需要实测——预处理的耗时经常超过模型本身。

### 9.4 时间与幂等

在线数据可能乱序、迟到或重复。运行时必须：

- 按 `timestamp` 而非到达顺序组织窗口。
- 对重复时间戳做幂等处理（同一时间戳的重复消息不改变状态）。
- 声明可容忍的迟到窗口，超出则丢弃并计数。

## 10. 存储、并发与平台

### 10.1 原子写与不可变性

所有制品写入使用「临时文件 + `os.replace`」模式（同一卷内原子）。写完后对 `source/` 下的原始文件设置只读属性，并在每次读取时校验 `source_sha256`（`TFV-702`）。

只读属性只防误操作，不防恶意修改，真正的保证来自指纹校验。

### 10.2 并发

- 一期采用**单写者**模型：导入、实验、发布均串行，通过文件锁互斥。
- **DuckDB 不支持多进程并发写**，单写多读。若 Experiment Runner 并行运行，各自写独立的结果文件，由单一进程汇总入库。
- 顺序 ID 分配见 [conventions §1.3](./conventions.md)。

### 10.3 Windows 注意事项

开发环境为 Windows，以下问题会在 Linux 上不复现：

| 问题 | 影响 | 对策 |
|---|---|---|
| 路径长度 260 字符限制 | `vault/datasets/<id>/rev_NNNN/canonical/...` 嵌套深，配合长数据集名易超限 | vault 根目录可配置且置于浅层路径；或启用长路径支持并统一用 `pathlib` |
| 文件系统大小写不敏感 | `variable_id` 大小写敏感语义被破坏 | 见 [conventions §1.2](./conventions.md)，不以 `variable_id` 直接命名文件 |
| 文件被占用时无法删除/替换 | 原子替换失败 | 确保读取使用上下文管理器及时关闭；DuckDB 连接显式关闭 |
| 默认换行 `\r\n` | 文本制品哈希跨平台不一致 | 所有文本制品以 `newline="\n"` 写入 |
| 默认编码非 UTF-8 | 中文字段乱码 | 所有 I/O 显式 `encoding="utf-8"` |

最后两条会直接破坏 [conventions §5](./conventions.md) 的哈希稳定性，必须在项目初期就统一。

## 11. 工具接口的返回约定

[architecture §6](./architecture.md) 列出了工具名，但未规定返回结构。为满足「Agent 不通过自由文本猜测实验是否成功」，建议统一信封 **[草案]**：

```json
{
  "ok": true,
  "tool": "tf_dataset_import",
  "id": "DC01_2026_CHILLER@rev_0001",
  "status": "IMPORTED_WITH_WARNINGS",
  "inputs": {"source_sha256": "…", "contract_version": "1.0"},
  "summary": {"rows": 525600, "variables": 87, "time_range": ["…", "…"]},
  "diagnostics": [
    {"code": "TFDC-505", "level": "WARN", "count": 3, "location": "data", "message": "…"}
  ],
  "artifacts": [
    {"kind": "quality_report", "path": "vault/…/quality.json", "bytes": 40213}
  ],
  "truncated": false
}
```

要点：

- **有副作用的工具必须返回稳定 ID**，Agent 后续引用该 ID 而非重新描述输入。
- **诊断聚合返回**，同类问题给 `count` 和少量样例位置，不逐行展开。
- **响应体必须有大小上限**（**[草案：32 KB]**）。超限时截断并置 `truncated: true`，同时把完整内容落为 artifact 供按需读取。这是「Agent 不直接读取海量原始数据」原则在接口层的强制手段——仅靠提示词约束不可靠。
- `tf_dataset_sample` 的返回行数必须有硬上限（**[草案：200 行]**），`tf_dataset_profile` 的分位数点位固定（如 min/p1/p25/p50/p75/p99/max），避免 Agent 通过反复调用变相拉取全量数据。

## 13. 测试基线

Phase 0/1 的测试应至少覆盖：

1. **每个错误码一个 fixture**：为 [conventions §7](./conventions.md) 中的每个代码准备一份最小 xlsx，断言代码、级别和 location 精确匹配。这是导入器唯一可靠的回归网。
2. **指纹稳定性**：同一逻辑数据经不同路径（Excel 重存、列序调换、行序打乱后排序）产生相同 `content_sha256`；任一值改动则必然改变。
3. **规范化幂等性**：`canonical_json(parse(canonical_json(x))) == canonical_json(x)`，用 Hypothesis 生成嵌套结构。
4. **跨平台哈希一致**：CI 至少在 Windows 与 Linux 各跑一次，比对同一 fixture 的所有哈希。
5. **泄漏检测**：构造含滚动特征的合成数据，验证未做 purge 时能被 `TFX-903` 捕获。
6. **端到端最小闭环**：小型 fixture 走完导入 → View → 实验 → 指标 → 模型包 → 冷加载冒烟，断言指标可复现。
