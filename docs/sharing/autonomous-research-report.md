## 1. 项目概览

### 1.1 要解决的问题

为某数据中心冷站建立一套可仿真的数字模型底座，覆盖冷机、板式换热器、冷冻／冷却水泵、冷却塔风机四类设备，能够回答「如果把某台设备的运行参数调到 X，功耗／换热量／流量／出水温度会变成多少」这类 what-if 问题。

传统路径的瓶颈不在算力，在**人的串行带宽**：一个假设试一天、一台设备试两周，而该站有 5 类设备、十余台机组。ThermoForge 的思路是把「做研究」这件事本身拆成机器可执行的循环，让 AI 在护栏内自主运转，人只在定义目标与拍板验收时介入。

### 1.2 交付定义

项目交付的不是 `model.pkl`，而是**模型包（Model Package）**，包含：

| 组成 | 文件 | 作用 |
|---|---|---|
| 签名 | `signature.yaml` | 输入／输出的物理量、单位、类型契约 |
| 约束 | `constraints.yaml` | 输入越界策略、物理约束 |
| 模型描述 | `model.yaml` | 契约版本、模型形式、血缘 |
| 权重产物 | `artifact/` | JSON/YAML/原生格式，**禁 pickle** |
| 指标 | `metrics.json` | 全部判据面的完整指标 |
| 验证 | `validation.json` | 时间切分记录、物理检查结果 |
| 数据血缘 | `dataset-lineage.json` | 数据集修订、视图 ID、视图哈希 |
| 研究血缘 | `research-lineage.json` | 目标／假设／实验编号 |
| 环境锁 | `environment.lock` | 复现所需的环境指纹 |
| 校验和 | `checksums.json` | 全部文件的 SHA-256 |
| 冒烟集 | `golden.parquet` | 冷加载回放用的黄金预测集 |
| 预处理 | `preprocessing.yaml` | 应用的预处理规则 |

## 2. 核心理念

整套系统的设计由三条原则推导而来。理解这三条，就理解了为什么系统是现在这个样子。

### 2.1 智能体永远碰不到原始数据

AI 的全部能力经过 `thermoforge_research.tools.TOOL_REGISTRY` 的 32 个工具，每个工具返回统一信封：

```
ok / tool / id / status / inputs / summary / diagnostics / artifacts / truncated
```

硬性限制：

- 响应体上限 **32 KB**，溢出转存为产物并置 `truncated=true`
- `tf_dataset_sample` 最多 **200 行**
- 剖面分位点固定，不接受自定义

**理由**：能直接读到全量数据的模型，会不自觉地把答案背进特征工程里。限制视野等于强制它做真正的建模而不是记忆。

**推论**：已知错误（`VaultError` / `ResearchError` / `ModelRegistryError` / 契约校验失败）一律转成 `ok=false` 的信封，从不抛异常。CLI 退出码不是成功信号——`exit 0` 只表示命令跑完了，包括工具级失败；调用方必须读 `ok`。

### 2.2 只有一个地方允许 AI 写代码，而那里完全无人审批

**模型实验室**（`research/model_lab.py`）是 AI 唯一能写代码的地方。流程：提交单文件模型模块 → AST 静态扫描 → 子进程五连检 → 版本化不可变入库。通过五连检即 `status=validated`，而 `validated` 是实验门禁唯一检查的东西（`require_runnable`，错误码 `TFML-006`）。

**全流程没有任何人类审批环节。** AI 自己提交、自己在真实数据上跑、自己读指标、自己改、自己以 `v(N+1)` 重新提交。

对照组是**数据预处理**：它只允许 AI 为预先注册的确定性变换提议参数，不允许生成代码；`status=proposed` 的规则集不能产生数据仓修订；审批强制 `actor=human`。

| | 模型实验室 | 数据预处理 |
|---|---|---|
| AI 可以写代码 | 是 | 否，只能提议参数 |
| 需要人类审批 | **否** | **是**（`actor=human`） |
| 改动的对象 | 假设 | 数据本身 |
| 撤销方式 | `deprecate()` 事后否决，不阻断已跑实验 | 不批准即不生效 |

**理由**：模型是假设，应该由证据杀死，而不是被审批队列拖死；数据是事实基底，改错了下游全污染。**放开哪里、收紧哪里，判据是「能不能自动证伪」。**

### 2.3 没有证据链的结论不算结论

151 条假设、169 次实验、87 条发现，每条发现挂着支撑它的实验编号；每个模型包携带完整的数据血缘与研究血缘。任何一个结论都能反查到：哪次实验、哪版代码（`code_version`）、哪个数据修订、哪个视图哈希。

这条原则的价值在泄漏事件中得到验证——正是靠它，才能在半个月后精确圈定 10 个受污染实验，并证明没有任何已发布模型包受影响（详见 §12.3）。

## 3. 系统架构

### 3.1 分层

| 包 | 职责 |
|---|---|
| `thermoforge_core` | 契约（Pydantic v2）+ 横切原语：规范化 JSON、指纹、顺序 ID、命名正则、单位、时间、错误码注册表 |
| `thermoforge_data` | TFDC-XLSX 导入／校验、不可变数据仓（Parquet + DuckDB 索引）、数据集视图、遗留工作簿适配、预处理规则库 |
| `thermoforge_models` | 模型实现：线性基线、冷机物理（Q·COP）、残差混合（物理 + XGBoost）、特征缩放 |
| `thermoforge_research` | 研究内核：账本、实验运行器（子进程隔离）、切分／泄漏、指标、物理检查、可建模性报告、白名单执法、编排器、模型实验室，以及 32 工具注册表与信封 |
| `thermoforge_runtime` | 模型包构建／校验、模型注册表 + 发布门禁、部署绑定、在线推理 |
| `thermoforge_cli` | `tf` 命令行，一个子命令对应一个工具，信封 JSON 输出到 stdout |
| `thermoforge_agent` | 内置对话智能体（OpenAI 兼容 chat completions + function calling） |
| `thermoforge_webui` | Streamlit 控制台：AI 副驾、数据浏览、质量诊断→处方、AI 研究循环实时进度、实验结果图表、模型注册表、报告导出 |
| `thermoforge_mcp` | MCP 服务器（stdio），向外部智能体暴露同一套工具注册表 |

### 3.2 运行时产物根目录

均已 gitignore，可通过 `tf --vault-root/--research-root/--models-root` 配置：

- `vault/` — 数据
- `research/` — 账本、实验、智能体会话
- `models/` — 模型注册表

### 3.3 智能体控制面（`harness/`）

`harness/` 只声明「智能体如何调用确定性工具」，不含任何研究逻辑：

- `harness/tools.json` — 工具名 → Python 入口的声明式清单，由 `tests/test_tools.py` 与 `TOOL_REGISTRY` 锁死同步
- `harness/prompts/{system,planner,copilot}.md` — 内置智能体、研究规划器、Web 副驾的提示词。**行为变更通常改这里，不改 Python**
- `harness/agent.toml` — OpenAI 兼容端点配置（gitignore）
- 工具 schema 由 `TOOL_REGISTRY` 生成，模型从不接触手写 schema
- 会话日志落在 `research/agent_sessions/*.jsonl`

单轮用户交互上限 `max_tool_rounds = 16`；耗尽必须降级为可续答的正常回答，而不是 UI 报错。

### 4.2 不可变性与原子写

- 数据仓修订与已完成实验**永不覆写**：内容变化 ⇒ 新修订（`TFV-701`、`TFX-904`）
- 每次产物写入都是临时文件 + `os.replace`
- 顺序 ID 来自 `core.ids.IdAllocator`（计数器文件 + 独占锁），永不复用
- 全程单写者模型；DuckDB 单写多读

### 4.3 两个指纹，一份规范化 JSON

| 指纹 | 输入 | 用途 |
|---|---|---|
| `source_sha256` | 原始字节 | 溯源 |
| `content_sha256` | 规范化后的逻辑内容 | 去重 |

重新保存过的 Excel 会改变前者但不改变后者。`canonical_json`（`core/canonical.py`）是 `docs/conventions.md` §5.1 的唯一实现：键排序、空键移除、排除非语义键、集合语义数组排序。

视图哈希：`view_hash = sha256(dataset_revision_id + "\n" + canonical_json(view))` —— **修订必须进哈希**，否则缓存会跨数据版本串味。

### 4.4 测量／派生的强制区分

2026-08-09 结案的两个 P0 数据问题（`docs/open-questions.md` Q10、`docs/issues.md` I-48）直接塑造了建模方式：

1. **工作簿的驱动序列是现场实测的，但约 296 万个单元格是 Excel 公式派生的** —— 因此强制 `source_kind` 测量／派生二分，这是 DD-16 白名单能生效的前提。
2. **COP 9~11 的区间对这个高温离心站是物理有效的** —— 这一条解锁了物理路线，否则 Q·COP 分解会被误判为数据错误。

## 5. 自动探索机制

### 5.1 研究闭环

```
目标 → 假设 → 实验 → 证据 → 结论 → 知识 → 新假设
  ↑                                          │
  └──────────────────────────────────────────┘
```

人只做一件事：写下研究目标契约——预测什么、允许用哪些输入、验收标准是多少、判在哪个面上。剩下的循环由编排器（`research/orchestrator.py`）自主驱动。

停止条件：

- 达到验收标准 ⇒ 转 `PUBLISH`
- 连续 N 轮无增益（默认 `no_gain_rounds=6`）⇒ 转 `STOPPED`，并要求规划器给出结构性结论
- 达到 `max_rounds` 上限

### 5.2 目标契约

每个研究目标（`research/goals/RG-*.yaml`）声明：

| 字段 | 含义 |
|---|---|
| `target` | 预测的目标列 |
| `candidate_inputs` | 候选输入白名单（DD-16 硬门禁） |
| `acceptance.evaluated_on` | **判据面**：`rolling_cv` / `A` / `validate` / `C` |
| `acceptance.r2_min` | R² 下限 |
| `acceptance.cvrmse_max` | CVRMSE 上限 |
| `acceptance.nmbe_abs_max` | \|NMBE\| 上限 |
| `acceptance.physics_violation_rate_max` | 物理违规率上限 |
| `acceptance.inference_latency_ms_max` | 推理延迟上限 |

**判据面是易错点**：面 A 是「训练截止后隔 N 天再考」，衡量的是漂移；`rolling_cv` 是折间均值，衡量的是稳定泛化。同一个门槛判在不同面上，含义完全不同——RG-0009 就是栽在这里（详见 §12.1）。

### 5.3 模型实验室

AI 提交一个单文件 Python 模型模块，须导出 `MODEL_FORMAT`、`INPUT_ROLES` 与实现 `fit` / `predict` / `save` / `load` 的类。

#### 5.3.1 准入流程

| 阶段 | 检查内容 | 不过的后果 |
|---|---|---|
| **AST 静态扫描** | 导入白名单、禁用子模块、禁用调用与双下划线、64 KB 上限 | 拒收，**不进入执行** |
| 五连检 · `interface` | 接口签名符合契约 | 整体判失败 |
| 五连检 · `fit_predict` | 能在合成数据上完成训练与预测 | 整体判失败 |
| 五连检 · `save_contract` | 产物只用 JSON/YAML/原生格式，禁 pickle | 整体判失败 |
| 五连检 · `roundtrip` | 存盘再读回，预测一致 | 整体判失败 |
| 五连检 · `determinism` | 同种子重跑**比特级**相同 | 整体判失败 |

五连检在**子进程**中执行，失败时返回**具体哪一项、错在哪**给 AI 自行修改。

#### 5.3.2 安全边界（必须明示）

AST 扫描跑在验证子进程执行候选代码**之前**，是唯一的自动预执行门禁。但它是**粗过滤，不是内核级沙箱**——`model_lab.py` 的模块文档字符串对此有明文说明。

接受这个风险的前提：受控内网环境、自有数据、子进程执行。**若要对外推广，或允许不受信任的模型提交代码，这一层必须替换为真实沙箱。**

#### 5.3.3 源码快照

运行器把模块源码快照进实验目录，`_child` 再复制到 `artifact/lab_source.py`，保证模型包自包含。`deprecate()` 是事后否决（任何 actor 均可），阻断未来引用但不影响已跑实验——它们保留自己的冻结源码快照。

### 5.4 实验运行

- 在**子进程**中执行，线程数环境变量（`OMP_/OPENBLAS_/MKL_NUM_THREADS`、`PYTHONHASHSEED`）在 numpy/sklearn 导入**之前**设置
- 缺随机种子 ⇒ `TFX-902`
- `environment_lock` 不匹配 ⇒ `TFX-901`
- 同机器 + 同锁必须**比特级**复现指标

### 5.5 无人值守编排

`scripts/autoresearch.py` 驱动长时循环，每圈返回：

- `rounds_failed` — 失败轮次
- `failures[]` — 含每轮 `detail`（**必须携带可行动的具体信息**，见 §12.5）
- `goal_best` — 扫描该目标全部 `EXP-*/spec.json` + `metrics.json`，返回声明判据面上的最优

## 6. 人机接口：主驾、副驾与外部智能体

系统对外暴露**三条 AI 通路**，它们共用同一个 `TOOL_REGISTRY`、同一套信封、同一套护栏，区别只在「谁在驱动」和「有没有界面能力」。

### 6.1 三条通路总览

| | **主驾**（内置研发 Agent） | **副驾**（网页控制台） | **外部智能体**（MCP） |
|---|---|---|---|
| 入口 | `tf agent`（终端 REPL） | Streamlit 控制台的「副驾」页 | `python -m thermoforge_mcp`（stdio） |
| 实现 | `thermoforge_agent.HarnessAgent` | 复用 `HarnessAgent` + 追加界面工具 | `thermoforge_mcp.server` |
| 提示词 | `harness/prompts/system.md` | `harness/prompts/copilot.md` | 由外部客户端提供 |
| 可用工具 | 32（全注册表） | 32 + `ui_goto` = **33** | **33**（32 − 1 + 2） |
| 能跳页／选对象 | 否 | **是** | 否 |
| 能跑实验 | 是 | **是** | 是 |
| 能开研究目标 | 是 | **是** | 是 |
| 能提交模型代码 | 是 | **是** | 是 |
| 能批预处理 | 否（发起 `tf_human_approval`） | 否（弹给人点） | 否（工具被排除） |
| 典型使用者 | 开发者调试、批量操作 | **不想点界面的工程师** | Claude Code 等外部 agent |

**共同底座**：工具 schema 全部由 `TOOL_REGISTRY` 自动生成，模型从不接触手写 schema；三条通路的会话都落在 `research/agent_sessions/*.jsonl`（当前 541 个会话，2.7 MB）——智能体行为异常时，这是第一个该看的地方。

### 6.2 主驾：内置研发 Agent

`thermoforge_agent` 是一个 OpenAI 兼容的 chat completions + function calling 智能体。

**配置**（`harness/agent.toml`，gitignore；模板 `agent.example.toml`）
优先级：CLI 参数 > 环境变量（`TF_AGENT_API_KEY` / `TF_AGENT_BASE_URL` / `TF_AGENT_MODEL`）> TOML。
`tf agent --check` 校验配置与端点连通性。

**行为约定**（写在 `harness/prompts/system.md`，**行为变更改提示词，不改 Python**）

1. 判断成败只看 `ok` 与 `status`，不凭自由文本猜测；`ok=false` 时读 `diagnostics` 的错误码向用户解释
2. 有副作用的工具返回稳定 ID，后续调用必须引用 ID，不得重新描述输入
3. 不能直接读海量原始数据——只能用 `tf_dataset_profile`（固定分位点）/ `tf_dataset_query`（聚合）/ `tf_dataset_sample`（≤200 行）
4. 白名单（DD-16）拒绝时**不要尝试绕过**，应向用户解释原因
5. 非首个假设必须引用已有证据（`basis`）
6. 内置模型路线是**闭集**，不要试探不存在的 estimator 名——闭集之外自己写模型代码走实验室

**工程约束**：单轮用户交互上限 `max_tool_rounds = 16`，耗尽必须降级为**可续答的正常回答**而不是 UI 报错。每条携带 `tool_calls` 的助手消息后必须跟**恰好一个**对应的工具结果——Chat Completions 拒绝孤立的消息组，这也是 `agent.py` 对历史做**规范化**而不是过滤的原因（提交 `ae52b97`）。

### 6.3 副驾：替人把控研究方向与进度

副驾是**使用者不想自己在界面上点来点去**时的代理。提示词开门见山：

> 你是 ThermoForge 控制台的副驾。使用者是工程师，但不想自己在界面上点来点去——他提问，你负责查清楚、讲明白，并把他带到该看的页面。

#### 6.3.1 它比主驾多的能力：`ui_goto`

副驾复用 `HarnessAgent` 的完整对话循环（function calling + 审批拦截 + 会话留痕），在**实例**的 `schemas` / `dispatch` 上追加一个界面工具 `ui_goto`：

```python
agent.dispatch = {**agent.dispatch, UI_GOTO_TOOL: self._ui_goto}
```

**追加而不是修改 `thermoforge_agent`** 是刻意的设计：界面能力属于界面，不该渗进 CLI 和 MCP 共用的 Agent 里。

`ui_goto` 让模型除了能查数据，还能决定「这个问题该看哪一页、该选中哪个实验」，并把结论一起带过去（`BANNER_KEY`，分析结论显示在目标页顶部）。

**可跳转的 8 个页面**（`navigation.PAGE_CATALOG`）：

| 页面 | 什么问题该来这一页 | 副驾可预选的控件 |
|---|---|---|
| `overview` | 整体进展：有几个目标、最近实验怎么样、有没有卡着等人处理的事 | — |
| `data` | 某个数据集里有什么变量、缺失多少、原始曲线长什么样 | `data_ref`, `data_series_vars` |
| `quality` | 这份数据能不能建模、有哪些阻断项、该怎么处理 | `quality_ref`, `quality_target` |
| `research` | **开始一轮自主研究，或新建研究目标与数据视图** | — |
| `results` | 某次实验跑得怎么样、误差在哪、几次实验哪个更好 | `results_exp`, `results_surface`, `compare_ids`, `compare_goal` |
| `models` | 已发布的模型包、版本状态、发布门禁过没过 | — |
| `report` | 把结果导成能发给别人的 HTML / Markdown / PDF | — |
| `settings` | 模型接口配置、密钥、网络连不上时的分层排查 | — |

`PageInfo.purpose` 字段写的是「**什么问题该来这一页**」而不是「这一页有什么控件」——因为它会直接进系统提示词，决定副驾往哪跳。

**一处工程细节**：`navigation.py` 只放一个**空注册表**，由 `app.py` 构造完 `st.Page` 后回填。原因是 `st.switch_page` 对函数式页面只认对象不认路径，而页面对象在 `app.py` 里构造、副驾模块又被 `app.py` 间接导入——直接互相 import 会成环。

#### 6.3.2 它替你把控什么

副驾的权限档位是使用者选定的「**全自动，除了 human-only 的**」。这意味着它可以自主完成：

| 动作 | 工具 | 说明 |
|---|---|---|
| 新建研究目标 | `tf_goal_create` | 定 target、白名单、验收判据与判据面 |
| 登记数据视图 | `tf_dataset_materialize` | 选特征与目标 |
| 提出假设 | `tf_hypothesis_create` | 非首个假设须引用已有证据 |
| 设计实验 | `tf_experiment_plan` | 含去重指纹校验 |
| **执行实验** | `tf_experiment_run` | 真实数据、真实时间切分、真实指标 |
| **提交自著模型代码** | `tf_lab_submit` | 静态扫描 + 五连检一过即 `validated`，**无需任何审批** |
| 停用走不通的模型 | `tf_lab_deprecate` | 事后否决 |
| 比较模型 | `tf_model_compare` | |
| 发布模型包 | `tf_model_publish` | 仍须过六道发布门禁 |
| 驱动自主研究循环 | 「AI 研究」页 | 目标 → 假设 → 实验 → 证据 → 结论 → 新假设 |

**唯一它做不了的事**：预处理审批。遇到需要审批的动作，它调用 `tf_human_approval` 发起，界面弹给使用者确认——**它不能替你批**。

#### 6.3.3 后台线程与审批拦截

一轮问答跑在**后台线程**里。原因很直接：副驾有权跑实验，而一次 `tf_experiment_run` 可能要几十秒到几分钟，放在 Streamlit 脚本线程里会把整个界面冻住。

审批拦截的实现：碰到 human-only 工具时，**后台线程阻塞等待**使用者在界面上点击；`APPROVAL_TIMEOUT_SECONDS = 900`（15 分钟），**超时按拒绝处理**——不让后台线程永远挂着。

事件流（`CopilotEvent`）实时回传界面，使用者能看到副驾正在调哪个工具、跳到哪一页、在等哪个审批。

#### 6.3.4 副驾要守住的硬规矩

提示词里明确列出、回答时必须守住的几条：

- **白名单是硬门禁**——派生量不能预测它的原料。本站的历史教训写进了提示词：`load = current_percent × 9672 / 100`，拿 `load` 预测功率能得到很漂亮的 MAPE，但毫无意义
- **看 `ok` 字段，不是看有没有报错**
- **指标只有一份实现**，不要自己算 RMSE/CVRMSE，读工具给的
- **指标是比率不是百分数**（CVRMSE 0.116 就是 11.6%）
- **R² 可以是负的**，负值表示模型比直接取平均还差——**这是有信息量的结论，不要藏着**
- **内置模型路线是闭集，不要试探名称**；闭集之外走模型实验室，且这条路自己走完
- **不确定就说不确定**，不要编 ID、不要编数字

### 6.4 外部智能体：MCP

`python -m thermoforge_mcp` 以 stdio 暴露 MCP 服务器，供 Claude Code 等外部智能体接入。

工具集 **33** 个：

```
32（TOOL_REGISTRY）
 − 1（EXCLUDED_TOOLS：tf_preprocess_approve，审批要求 actor=human）
 + 2（EXTRA_TOOLS：tf_status / tf_experiment_report，MCP 专用便捷包装）
= 33
```

**设计要点**：审批工具被**排除**而不是被拒绝——外部智能体连看都看不到它，从根上杜绝「反复尝试审批」的浪费。

### 6.5 唯一的人工闸口

三条通路加起来，人必须出现的地方只剩下**一处**：

> **预处理规则审批**（`tf --actor human preprocess approve`，或智能体的 `tf_human_approval` 往返）

这不是疏漏，是 §2.2 那条原则的直接结果——**预处理改的是数据本身，验不了，所以收紧；模型改的是假设，能自动证伪，所以放开。**

## 7. 护栏体系

护栏的验收标准只有一个：**它抓到过什么**。以下六条各配一次真实拦截。

### 7.1 候选输入白名单（DD-16）

**规则**：`whitelist.py` 执法两次——目标级（条目必须存在于该修订，且不得 `source_kind=derived`）与实验级（视图特征 ⊆ 白名单，视图目标 == 目标目标）。

**抓到的**：该站的冷机 `load` 列不是实测，是 `current_percent × 96.72` 反算的（`load.max / current_percent.max = 96.72 = 9672/100`，即额定冷量／100）。拿它预测冷机功耗能得到 MAPE **4.35%** 的漂亮结果——纯粹的循环论证。白名单直接堵死这条路，`current_percent` 也一并排除（它是 `load` 的原料，与目标同源）。

### 7.2 可建模性门禁

**规则**：`modelability.py` 是语义层门禁，检查派生链、同源相关、设备多样性、物理合理性、工况覆盖。FAIL 阻断进入建模。

**抓到的**：泵频与泵功耗相关系数 **0.996**（比风机那次的 0.983 更高）。看着是好特征，实际是相似律 `P ∝ f³` 的同一个物理量换了写法。门禁标记同源，逼迫改换标签——RG-0020 因此把标签从功耗改为流量。

**门禁的边界也要说清**：冷却水泵那次，实测 `Q·|ΔT|` 变异系数只有 0.080（Q 自己 0.164），`corr(Q,|ΔT|) = −0.839`，这是能量守恒 `Q·ΔT ≈ 排热量/cp` 显形——ΔT 是被流量决定的，不是原因。但它**不违反 DD-16**（ΔT 不是由流量算出的列），同源检测也抓不到（0.839 < 0.98 阈值）。**这是用途层面的判断，只有懂这个回路的人看得出来。** 详见 §9.6 的使用限制。

### 7.3 指标唯一实现

**规则**：`research/metrics.py` 是 RMSE / MAE / MAPE / CVRMSE / NMBE / R² 的唯一实现（比值刻度，非百分数）。建模代码**不得自行计算**。

**抓到的**：

- MAPE 丢弃 `|y| < y_floor` 的样本，并报告有效占比；低于 0.8 触发 `TFX-905`
- `mean(y) ≈ 0` 时 CVRMSE / NMBE 返回 `None`，而不是一个看着挺像回事的数
- 指标输入含 NaN 视为缺陷，直接抛错

这些是最容易被无意识美化的地方，收进一份实现后就再也美化不了。

### 7.4 按时间切分，不按行数

**规则**：切分边界向下取整到分辨率倍数（本项目 900 秒），记录为时间戳；训练尾部 **purge**、验证头部 **embargo**（默认 2700 秒 = 45 分钟）；重叠或间隔不足 ⇒ `TFX-903`。

**抓到的**：暖通数据 15 分钟采样，随机切分等于把相邻时刻分别丢进训练集与测试集。任何一次随机切分都能把精度「提升」到不可信水平，而报错让它根本跑不起来。

### 7.5 环境锁与比特级复现

**规则**：见 §5.4。

**抓到的**：重跑 EXP-0058 / EXP-0061 时指标差了 5 倍。规格文件逐字节相同，唯一差别是 `code_version`（`684ef057` → `c2134bc2`），中间夹着提交 `0b7c1dc 堵死实验室模块的目标列泄漏`。顺线追查证实：**那两个实验当初在偷看答案**。

`code_version` 是**唯一能暴露跨提交指标不可比**的字段。完整复盘见 §12.3。

**反向验证**：`wx-hx-heat-transfer@1.1.0`（EXP-0086，假设 H-0059）与 `wx-hx-heat-transfer-static@1.0.0`（EXP-0177，假设 H-0040）是两次独立实验，配置相同（VIEW-0042 + `gbdt_static@v1` + 同超参 + 同种子），**指标完全一致**（CVRMSE 0.0182 / NMBE +0.0027 / R² 0.759）。这是确定性护栏的正面证据。

### 7.6 发布六道门禁

**规则**：模型包进入 production 必须过六道门（`runtime/registry.py`）：

| 门禁 | 检查 |
|---|---|
| `integrity` | 文件齐全且校验和一致 |
| `signature_tfom` | 与 TFOM 对象模型注册表兼容 |
| `acceptance` | 硬性验收条件（在声明判据面上） |
| `latency` | 推理延迟上限 |
| `smoke` | **冷加载 + golden 比对**（全新解释器，`TFM-1005`） |
| `rollback_recorded` | 回滚目标已记录 |

版本状态机：`candidate → validated → approved → production → deprecated → retired`，**回滚是唯一的反向边**。

**抓到的**：塔风机逐台模型跑到 **6.08%**，而 RG-0028 的验收线是 **5%**。门禁把它卡在 `candidate`，发不出去。要发只有一条路——人明确修改判据，并留痕说明新阈值的性质。实际留痕原文：

> 2026-08-20 判据修订：`{'cvrmse_max': 0.05}` → `{'cvrmse_max': 0.065}`。理由：需求方明确指示带着未达标项发布（知悉最优为 6.08%、判据为 5%）。**这个 0.065 是为容纳既有结果而放宽，不是工程论证得出的阈值**，后续不要把它当作已验证的精度要求。

**没有「差不多就行」这个选项。**

### 11.2 源码范例

以最终发布的 `pump_power_per_object_affinity_v1@v1` 为例，这是 AI 自己写的完整模型（节选）：

```python
import json
import os
import numpy as np

MODEL_FORMAT = "thermoforge.lab.pump_power_per_object_affinity_v1"
INPUT_ROLES = ["frequency"]


class PerObjectPowerLawModel:
    def __init__(self, seed=None):
        self.seed = seed
        self.params_ = {}
        self.global_params_ = None

    def _fit_params(self, x, y):
        best = None
        for b in np.linspace(2.0, 3.5, 61):          # 指数网格搜索
            X = np.column_stack([(x / 50.0) ** b, np.ones_like(x)])
            coef, _, _, _ = np.linalg.lstsq(X, y, rcond=None)
            pred = X @ coef
            rmse = float(np.sqrt(np.mean((y - pred) ** 2)))
            if best is None or rmse < best[0]:
                best = (rmse, float(b), float(coef[0]), float(coef[1]))
        return best[1], best[2], best[3]

    def fit(self, df, y):
        y = np.asarray(y, dtype=float)
        freq = np.asarray(df["frequency"], dtype=float)
        obj_col = [str(v) for v in df["object_id"]]   # ← 逐台分组的关键
        mask = freq > 1e-9
        self.params_ = {}
        for obj in np.unique(obj_col):
            m = np.array([mask[i] and obj_col[i] == obj for i in range(len(obj_col))])
            if np.sum(m) < 5:
                continue
            b, a, c = self._fit_params(freq[m], y[m])
            self.params_[obj] = {"b": b, "a": a, "c": c}
        # 全局兜底，供未见过的 object_id 使用
        if np.sum(mask) >= 5:
            b, a, c = self._fit_params(freq[mask], y[mask])
            self.global_params_ = {"b": b, "a": a, "c": c}
        else:
            self.global_params_ = {"b": 3.0, "a": 0.0, "c": 0.0}
        return self

    def predict(self, df):
        freq = np.asarray(df["frequency"], dtype=float)
        obj_col = [str(v) for v in df["object_id"]]
        preds = np.zeros(len(freq), dtype=float)
        for i, (obj, f) in enumerate(zip(obj_col, freq)):
            if f <= 1e-9:
                preds[i] = 0.0                        # 停机即零功耗
                continue
            p = self.params_.get(obj, self.global_params_)
            preds[i] = p["c"] + p["a"] * (f / 50.0) ** p["b"]
        return preds

    def save(self, directory):
        os.makedirs(directory, exist_ok=True)
        # ... 序列化为 JSON，不用 pickle
```

**值得注意的几点**：

- 显式声明 `INPUT_ROLES`，供门禁与规划器交叉核对（见 §12.5）
- 用 `object_id` 分组——这是第二轮才做对的事，第一轮的模块没引用它，导致 8 台泵拟合成一条全局曲线，成绩 10.49%
- 停机（f ≈ 0）直接返回 0 功耗，而不是让幂律外推
- 提供全局兜底参数，处理未见过的 `object_id`
- `save()` 序列化为 JSON，符合 `save_contract` 检查

## 12. 自我否定记录

这一节是本文档最有价值的部分。以下五次，每一次都是先有了看起来漂亮的结果，然后由系统自己拆掉。

### 12.1 判据面判错 —— RG-0009 → RG-0012

**问题**：RG-0009 把 CVRMSE 门槛 0.12 判在**面 A**上。但 0.12 这个数是从**按周分块基线**推出来的，而面 A 是「训练截止后隔 23 天再考」，衡量的是漂移，不是稳定泛化。**门槛的推导口径与判定口径不一致。**

**处置**：作废 RG-0009，建立 RG-0012，判据面改为 `rolling_cv`（折间均值），与门槛推导口径对齐。同时把两侧流量纳入白名单——离线实测显示 CH01/CH03 各降 1.3~4.9 个百分点。

**沉淀的教训**：`acceptance.evaluated_on` 必须与门槛的推导方式匹配。这个字段是最容易被忽略、也最容易让结论失真的地方。

### 12.2 白名单混入派生量 —— RG-0012 → RG-0015

**问题**：RG-0012 的白名单里含 `runtime_accum`（累计运行时长）。这是一个随时间单调增长的量，模型可以借它间接识别时间位置，从而在时序数据上取得虚高成绩。

**处置**：建立 RG-0015，从 `candidate_inputs` 剔除 `runtime_accum`（白名单由 16 项减至 15 项）。

**遗留**：`wx-chiller-power-static@1.0.0` 建在剔除前的 VIEW-0044 上，仍含 `runtime_accum`（已在 §9.10 标注）。

### 12.4 「群模型比逐台准」是分母幻觉

**表面现象**：塔风机群总功耗 `wx-ct-fan-power-total` 判据面 CVRMSE **2.43%**，逐台 `wx-ct-fan-power-unit` **6.08%**。看上去群模型完胜。

**问题**：这两个数的**分母不同**。群模型的 CV_y 是群总功耗的变异，逐台模型的 CV_y 是单台功耗的变异；单台功率小、噪声占比大，相对误差天然更高。直接并列是误导。

**正确做法**（`scripts/analyze_fan_aggregation.py`）：把逐台模型的预测**按时间戳加总到群口径**，再与群模型在同一面上比。指标全部走 `research/metrics.py` 的规范实现。

| 判据面 | 逐台口径 | **加总到群口径** | 群 XGBoost | 加总增益 |
|---|---|---|---|---|
| A | 4.51% | **3.10%** | 3.55% | 1.46× |
| validate | 5.41% | **4.46%** | 6.56% | 1.21× |

**结论：逐台物理模型加总后，在两张面上都胜过群模型。** 群模型的「优势」纯属分母错觉。

**附带的有行动价值的结论**：逐台误差两两相关系数 **+0.3144**（中位 +0.3612），不独立。因此 12 台加总只买到 1.2~1.5 倍的误差抵消，而非理想独立的 √12 = **3.4641** 倍。

推论：**继续压逐台的随机误差，对群口径收益有限；该压的是共模偏差。** 这直接指出了下一轮的投入方向。

**留痕**：发现 **F-0087**，`supported_by = [EXP-0170, EXP-0092]`，产物 `research/tool_artifacts/analysis/ct_fan_unit_vs_group.json`。

**局限声明**（已写入发现正文）：EXP-0092 与 EXP-0170 建在不同视图上，跨实验的面对面比较仅供参考；真正精确的是 EXP-0170 内部的「逐台 → 加总」分解。

### 12.5 平台缺陷：让机器看不懂自己的失败

这一条不是研究结论，是**自动化系统的核心工程教训**。

**现象一：RG-0028 七轮废六轮**

- 三轮崩在 `KeyError: 'fan_freq_mean'` / `'fan_run_count'`——模块声明的 `INPUT_ROLES` 里的列名在任何视图里都不存在
- **根因**：`_lab_check.py` 的 `_synthetic_frame(roles)` 用模块**自己的声明**造测试数据，所以五连检永远发现不了「声明的列不存在」
- **修复**：从 `LabStore` 外露 `input_roles`，在规划阶段用真实视图交叉核对（`planner.py::_lab_view_error`）

- 另有四轮跑出**逐位相同**的结果（0.0645 / −0.0107，跨 VIEW-0071/0072/0073）
- **根因**：去重指纹里含 `view_id`，但模块 `ct_fan_tower_shared_b` 硬编码 `INPUT_ROLES=['frequency']`——换视图对它毫无影响，系统却以为是新实验
- **修复**：`_fingerprint_scope()`——对 lab 类模型，指纹用「目标列 + 实际读取的列」而非 `view_id`

**现象二：RG-0023 七轮里五轮失败，报错只有「结构校验未通过」**

- **根因**：`detail = summary.get("error") or summary.get("validation") or summary`，而 `error` 字段永远非空，导致具体的检查项失败信息永远取不到
- **修复**：`_lab_failure_detail()` 逐项提取 `error` / `violations` / 未过检查的 `name` 与 `detail`

**教训**：报错信息里少写一句「哪一项检查没过、具体错在哪」，AI 就会在同一个坑里重复摔七轮。**这不是日志问题，是自动化系统的核心吞吐瓶颈。** 自动探索的真实成本结构里，很大一块是让机器能看懂自己的失败。

## 14. 局限与风险

**本节需要如实转述，不要在对外材料中删减。**

### 14.1 没有节能收益数字

**13 个模型全部完成生产注册，但没有任何一个做过部署绑定，也没有实测节能收益。**

因此本项目的效益口径是「建模生产力 + 结论可信度 + 数据资产诊断」，**不是运营收益**。任何往「节电 X%」方向的表述都缺乏证据支撑。

### 14.2 两处为容纳结果而放宽的判据

这两处阈值**不是工程论证得出的**，留痕中已明确标注，引用时必须带上这个限定：

| 目标 | 原阈值 | 放宽后 | 影响的模型 |
|---|---|---|---|
| RG-0012 | `nmbe_abs_max = 0.02` | **0.035** | CH01（2.47%）、CH03（3.40%） |
| RG-0028 | `cvrmse_max = 0.05` | **0.065** | `wx-ct-fan-power-unit`（6.08%） |

**RG-0012 放宽的副作用**：该目标同时管着 `wx-chiller-power-static`，因此该目标下后续发布的偏差门槛一并放宽了。若要隔离，应把冷机通用功耗拆成独立目标。

对照：RG-0017、RG-0020、RG-0023、RG-0026 的判据修订属于**判据退化改判**（R² 在 CV_y → 0 时失效），有工程依据，性质不同。

### 14.3 面 A 样本不足的两个模型

`wx-chiller-power-ch02` 与 `wx-chiller-power-static` 在面 A 上**只有 6 个样本**，该面指标（35.22% / 26.97%）无统计意义，不得引用。二者的有效判据在 `rolling_cv` 面。

### 14.4 使用口径限制

`wx-chwp-flow-total` 只能作**虚拟流量计**使用，**不能用于 what-if 仿真**（白名单含流量的下游后果量 `delta_t` / `power_total`）。详见 §9.6。

### 14.5 安全边界

模型实验室的 AST 扫描是**粗过滤，不是内核级沙箱**。当前风险可接受的前提是受控内网、自有数据、子进程执行。对外推广前必须替换为真实沙箱。

### 14.6 结构性不可达的结论

- **RG-0020 冷冻泵流量**：R² ≥ 0.90 在窗内近乎常数的目标上不可达，真实成绩应表述为「±2.5%（±73 m³/h）」
- **RG-0022 冷却泵 what-if 流量**：瓶颈是缺测点，不是模型形式。候选输入内无论怎么换模型都无法创造不存在的系统阻力信息

### 14.7 未完成部分

Phase 5（容器化、队列、多站点、多智能体）未启动。当前是单机单写者模型。

## 15. 可迁移方法论

以下五条与暖通领域无关，适用于任何让 AI 自动干活的场景。

### 15.1 先把验收标准写进契约，再开始跑——包括判在哪个面上

事后定标准等于让结果决定标准。本项目改判据改过多次，但每次都留痕、说明理由、并明说新阈值是否为工程推导所得。**改标准不可耻，偷偷改才可耻。**

判据面（`evaluated_on`）尤其关键——同一个门槛判在「漂移面」与「折间均值面」上，含义完全不同。RG-0009 就栽在这里。

### 15.2 让 AI 写代码的地方必须能自动验；不能自动验就别让它写

五连检里最关键的是 `determinism` 与 `roundtrip`——它们保证产出物是个真东西，不是一次侥幸。

反过来，预处理会改数据本身、验不了，所以那里强制人工审批。**放开哪里、收紧哪里，判据是「能不能自动证伪」，不是「重不重要」。**

### 15.3 每条结论挂证据 ID，否则不算结论

成本极低（存个编号），收益极高。本项目能在半个月后查清泄漏影响范围、并证明已发布包干净，全靠这一条。

### 15.4 护栏的验收标准是「它抓到过什么」

写完一条规则就问：它拦下过哪次真实事故？答不出来的多半是自我感觉良好。本文 §7 的六条护栏每条都答得出来。

### 15.5 把「让机器看懂自己的失败」当成一等公民

报错里少写一句「哪一项没过、错在哪」，AI 就会在同一个坑里重复摔七轮。这是自动化系统最容易被低估的吞吐瓶颈。

**具体做法**：失败信封必须逐项提取 `error` / `violations` / 未过检查的 `name` 与 `detail`，而不是塞一个笼统的字符串。

### 16.2 判据面与 R² 退化规则（plan §13）

R² = 1 − (CVRMSE / CV_y)²。当判据窗口内目标近乎常数（CV_y → 0），R² 必然塌陷，与模型好坏无关。

| 窗内 CV_y | 判据选择 |
|---|---|
| > 0.15 | `r2_min` 可用 |
| 0.05 ~ 0.15 | 谨慎带，R² 在部分折上不稳 |
| < 0.05 | **必须用 CVRMSE + NMBE** |

**关键**：要算的是「判据面**窗口内**的 CV_y」，不是全集 CV_y。全集 CV_y 只决定门槛的数量级，真正决定 R² 能不能用的是窗内波动。本项目在一晚上踩到同一个坑三次（风机周折、冷冻水泵、CH03 退化折）。
