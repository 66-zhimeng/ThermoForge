# ThermoForge V2 使用指南

V2 由 ThermoForge 软件在后台启动一个主 Codex 和五个候选 Codex。每个实例有独立进程、会话、工作目录和研究轨迹；主智能体组织方向、分配任务、比较路线，也可以开展自己的实验。网页、CLI 与外部研究副驾驶通过同一服务控制这些工作。

每条轨迹可以查资料、登记想法、实现模型、请求实验、根据结果修订并继续研究。六个 Codex 研究实例独立并行，当前训练实验经过中心队列，在后台服务中全局串行执行。

新运行的主智能体与五个候选默认统一使用 **GPT-6 Astra（`gpt-6-astra`）、最高思考强度 `ultra`、普通速度（关闭 Fast）**。软件为各实例和每轮请求显式指定普通速度，不继承本机快速模式；这不修改本机全局 Codex 设置。旧运行的配置和历史证据保留原记录，之前未记录速度的实验不补写为已验证普通速度。

速度配置依据 [Codex 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)（Fast 映射为 `priority`）和本机 0.153.4 的 App Server 协议。已通过不调用模型的启动核验确认 `gpt-6-astra / ultra / default`；六实例、逐轮覆盖、恢复和异常配置由确定性协议测试验证。运行时若未确认指定配置，或通知切换到其他模型，研究会停止并保留诊断。

新建研究默认使用 `research_mode="autonomous"`：统一问题、数据和预算，由候选自行选择研究方法，不再规定所有候选依次训练相同的线性回归和岭回归。旧的 `acceptance` 模式保留给固定步骤的功能验收脚本；未记录模式的旧运行恢复时也保留原行为。运行模式不能在中途切换。

## 1. 准备软件、数据和目标

在软件目录完成依赖安装：

```powershell
uv sync
.venv/Scripts/tf v2 prepare
```

`prepare` 返回真实发现的数据修订、目标、运行默认值和 Codex 准备情况。`available=false` 或非空错误表示仍需处理相应缺项；安装界面和查看既有数据不代表 Codex 研究已经可运行。Codex 认证沿用本机正常配置，不要把认证文件、API 密钥或访问令牌复制到插件或候选工作目录。

当前 Codex App Server 协议基线为 **0.153.4**。Windows 未设置 `TF_CODEX_BIN` 时，软件优先自动发现 Codex 桌面应用自带且版本受支持的 CLI，再查找 PATH 中的 `codex`。通常无需另装 npm CLI；如需指定安装位置，可设置 `TF_CODEX_BIN`，再通过 `prepare` 核对可执行文件和所需版本。实际协议版本与认证在研究实例启动时验证，失败原因显示在轨迹与运行事件中。

研究需要现有 `RG-...` 目标和固定数据修订。可在原有「AI 研究」页面创建目标和 Dataset View，或通过已有数据/研究工具完成准备。候选输入白名单、数据来源测量/派生语义、时间切分、purge/embargo、物理检查继续生效。来源门禁不会替你批准数据预处理。

## 2. 从网页启动与观察

用现有 `启动网页版.bat` 打开软件，进入「V2 研究运行」。在「新建研究」选择真实目标与数据修订，可填写已有 view ID，设置研究要求与预算。模型与思考强度预填为上述统一配置并只读显示。

| 配置 | 含义 |
|---|---|
| 主 Codex ＋ 5 个候选 | 首期正常研究配置；共六个独立研究实例 |
| 单 Codex 对照基线 | 用户进行对照时选择；不自动替换正常配置 |
| Codex 模型 / 思考强度 | GPT-6 Astra / `ultra`；主智能体、候选和单智能体基线使用同一默认配置 |
| 请求速度 | 普通速度，关闭 Fast；每轮显式使用 `default` 服务档位 |
| 全局实验上限 | 主智能体和候选共同使用，实验提交前由服务检查 |
| 每条轨迹实验上限 | 限制单条路线消耗的实验额度 |
| 全局 token 预算 | 默认 1,000,000；累计输入与输出 token 的软上限，包含缓存输入，不等于费用或底层模型的硬中断保证 |
| 每条轨迹执行片段上限 | 至少 3，给方案、实验和结题留出机会；一次回复结束不自动等同结题 |
| 实验并发数 | 当前固定为 1：后台服务全局串行执行训练实验，六个 Codex 的研究仍独立并行 |
| 独立探索 | 全程各自探索，候选之间不分享研究内容，结题时由主智能体比较；重复方案分别执行 |
| 保留优质路线 / 根据进展调整 | 各自完成首轮方案和实验反馈后，主智能体才分享明确引用的证据、比较并调整路线 |
| 共享后复用相同实验结果 | 仅共享策略可选，默认关闭；协议、模型与源码身份完全一致时可复用结果，报告标明来源，不当作独立复现 |

当前 V2 实现的是独立探索、证据比较和受控路线调整。完整 EvoX 的搜索策略元进化及其研究收益尚未在本项目中实现或验证；多智能体是否改善效果，需要按相同预算、评价协议和重复运行进行对照。

预算耗尽时，服务按可观测用量请求停止后续工作；正在执行的模型请求和用量上报存在时间差，可能出现超额窗口。软件不会自动增加预算、购买额度或补充账号限额。用户可调整运行预算，但这不会改变底层账号的可用额度。

自主研究按以下步骤推进：

1. 候选分别登记想法与来源，再用 `research_proposal_commit` 冻结首轮模型、参数和代码版本。主智能体与其他候选在该阶段看不到其私有内容。各首轮方案齐备后，服务才开放实验；明确失败等无法继续的轨迹可按状态退出等待。
2. 候选用 `proposal_id` 执行完全匹配的方案，只接收验证反馈。每次结果都登记发现与解释；后续方案必须引用自己最近一次已结束的实验及其分析。方案追加版本，旧方案不改写。
3. 完全相同的实验不能换个想法编号就作为新探索提交。有复现理由时声明 `purpose="replicate"`，保留实际重复执行的记录。不同候选自行选择相同方法是允许的，软件不会强迫制造差异。
4. 候选需要停止时，先提交覆盖全部已结束实验、想法和分析的报告，再用 `research_stop` 引用证据说明理由。有阶段报告或做完两次实验，都不会自动终止仍有预算的研究。

实验额度或执行片段将用尽时，服务转入整理报告与停止依据的收尾阶段。若 token 限额、服务中断等使收尾也无法完成，页面保留预算耗尽或中断状态，不伪称完整结题。达到预算上限不等于达到研究目标。

自主模式还会提前估算报告预算：至少预留总 token 预算的 25%，并参考各实例最近一次实际用量估算候选报告和主报告的成本，取较保守的值。进入预留区后，软件持久登记 `research_closure`，停止接受新增方案和实验，继续归账在途实验并允许发现、报告、停止工具。该规则是收尾估算，无法保证所有模型请求都在上限内完成。恢复相同预算的运行仍处于收尾；只有用户明确增加预算后才重新评估，已停止的轨迹不会自动重新探索。

点击「启动后台研究」后取得稳定的 `run_id`。在「运行与报告」查看当前研究阶段、已冻结方案、停止决定，以及各轨迹的 PID、会话、用量、错误和实验队列。方案表显示版本与所依据的实验，停止表显示理由及证据。实例存在与当前有研究进展是不同状态；等待首轮方案齐备、等待实验或空闲不等于失败。

关闭网页或外部对话不会发送取消请求。需要停下时使用页面或工具的暂停/取消操作，并查看服务返回的实际状态。在途实验的处理以状态和后续事件为准，不要把“暂停中”解释成“已经全部停止”。恢复仍使用同一个 run；实例重启后 PID 可改变，轨迹记录继续保留。

后续研究要求和预算可以通过页面调整。服务拒绝过期版本、低于已预留实验量的上限以及对冻结评价协议/拓扑的修改。需要不同目标、数据或评价协议时创建新运行。

## 3. 从 CLI 或对话控制

CLI 提供 `tf v2 prepare/list/start/status/events/control/report`。先用帮助查看当前安装版本的参数：

```powershell
.venv/Scripts/tf v2 --help
.venv/Scripts/tf v2 start --help
```

启动配置使用 JSON 文件，避免在命令行中手工转义复杂研究要求。以下字段值需选用 `prepare` 实际返回的对象：

```json
{
  "goal_id": "RG-0001",
  "dataset_ref": "CHILLER@rev_0001",
  "candidates": 5,
  "research_mode": "autonomous",
  "max_experiments": 20,
  "max_experiments_per_track": 4,
  "max_turns": 8,
  "token_budget": 1000000,
  "strategy": "independent",
  "reuse_experiments": false,
  "experiment_workers": 1,
  "guidance": "提高冷机功率预测精度。自主选择方法；每项想法登记真实来源、预测和反证条件，依据自己的实测反馈修订，保留失败实验与负结果。"
}
```

```powershell
.venv/Scripts/tf v2 start --config-file research-config.json --idempotency-key my-first-research-20260906
.venv/Scripts/tf v2 list
```

幂等键标识一次逻辑启动请求：网络错误后重试相同研究时沿用原键，开始另一项研究时换新键。取得实际 `run_id` 后，可用 `tf v2 status <run_id>` 查询、`tf v2 events <run_id> --after 0` 读取事件，或用 `tf v2 report <run_id>` 生成报告。控制命令形如 `tf v2 control <run_id> pause --expected-version <最新版本>`；配置调整使用 `update --changes-file changes.json`。

参数已明确的对话也可以直接启动，不需要先去网页点击。外部副驾驶通过 `tf_v2_prepare`、`tf_v2_start`、`tf_v2_list`、`tf_v2_status`、`tf_v2_events`、`tf_v2_control`、`tf_v2_report` 控制软件；它不是内部主智能体，不负责逐轮发送“继续”。

需要候选之间分享时，在新建配置中将 `strategy` 设为 `top_k` 或 `adaptive`；如需复用，再显式设置 `reuse_experiments=true`。独立模式禁止开启复用。单 Codex 对照使用 `candidates=0`，同样先冻结方案、按反馈修订并有依据地停止。

仓库提供 `plugins/thermoforge` 插件目录与说明。该目录仅作为可分发交付，不自动安装到用户个人插件目录，不修改全局配置。MCP 连接中断后可重连并查询原 run；同一逻辑启动请求重试应沿用幂等键，避免产生重复研究。

## 4. 阅读报告：看证据与条件，而不只看最好分数

综合报告和各轨迹报告使用同一事实层，提供 JSON、Markdown 和自包含 HTML 下载。报告保留：

1. 实际来源、稳定 URL/DOI、阅读范围及登记核验方式。
2. 实验前想法、研究方向选择理由、预测与反证条件。
3. 实际模型、实验请求、验证结果和失败原因。
4. 观察、解释、限制以及下一步需要验证的问题。
5. 主智能体保留、淘汰、分支或修订路线的依据。

HTML 报告默认展示研究流程图：主智能体的任务、候选各自的想法、冻结方案、实验、验证指标、停止依据和研究报告，以及单独列出的外部留出评价。点击节点可查看选择方向的理由、预测与反证条件，并沿引用跳转到来源、历史实验或发现。修订版本显示父实验和分析依据；复用结果标明原始作业，不能算作又一次独立实验。可按轨迹筛选，展开完整文字报告查看全部记录。连线依据实际登记的引用或消息，不代表候选之间发生过未记录的讨论；节点排列也不等于精确执行时间。当前研究实例并行，而训练实验仍由单个执行器串行排队。

`metadata`、`abstract`、`excerpt`、`fulltext` 表示不同阅读范围，不能混称阅读全文。自主假说允许没有论文，但应清楚说明它是推测。实验失败可能来自实现、数据或预算；报告不会把未产出有效结果写成零分，也不会自动解释成假说被证伪。

比较使用冻结协议指纹和明确的 `validate` 指标。不同数据修订、切分、目标、物理约束或缺少口径的实验不直接排名。一个验证指标最优不等于所有验收标准通过，也不等于模型已发布。运行完成或取消后，服务可将预先选定实验的 A/B/C 留出结果放入外部报告；选择依据和实际指标单独列出，不返回研究智能体。预算耗尽、等待输入等可恢复状态不提前开放留出反馈。缺少留出结果不表示达标。

报告中的缺失引用、尚无实验、未完成路线和未知用量都会显式保留。Codex 未提供的精确 token 分项或费用表示“不可得”，不能按零计算；六个实例共用账号时也可能共用服务额度和限流。

## 5. 运行目录与诊断

软件继续使用现有 Vault、研究与模型目录；GUI、CLI 与插件应配置相同的 `TF_VAULT_ROOT`、`TF_RESEARCH_ROOT`、`TF_MODELS_ROOT`。V2 状态由独立服务持久保存，候选有自己的研究工件目录，避免同时改写另一条路线。

| 现象 | 查看什么 |
|---|---|
| 无法启动 Codex | `prepare` 的安装与所需版本；实例启动后的协议、认证错误见轨迹事件 |
| 页面没有显示新研究 | 实际连接的工件根、`run_id` 和运行列表 |
| 进程存在但不继续 | 轨迹阶段、最近事件、等待实验与必要输入状态 |
| 单条候选失败 | 该轨迹错误和失败次数；其他候选的状态分别核对 |
| 无有效指标 | 实验失败分类、来源/想法校验、视图和协议指纹 |
| 修改配置被拒绝 | 最新运行版本、已预留预算及可变字段范围 |
| 插件无法定位软件 | `TF_PROJECT_ROOT` 或插件本地 `connection.json`；先执行 launcher 的 `--check` |

正常使用不需要六个独立窗口。验证“六实例并发”时，应核对六个独立 PID/会话及有重叠的真实工作区间；单靠页面的六行记录不能证明完成并发研究。判断多智能体是否改善研究质量，还应比较单 Codex 与六实例的预算、验证/留出口径和重复运行结果；架构本身不预先保证提升。

早期固定功能验收中，五个候选使用相同合成数据、划分、随机种子，并按预设要求依次训练 linear 和 ridge(α=1)，结果相同是预期现象。该运行只能证明实例管理、实验工具与报告链路可用，不能证明自主选题、文献驱动创新或多智能体的质量收益。新自主运行需要单独留存实际方案、反馈修订和成本，再开展相同总预算的单智能体对照；五条路线不同也不能替代质量评价。
